# ARCHITECTURE — AMOLIE

Версия 0.4 (черновик для утверждения). Все технологические решения в этом документе — **предложения**, требующие подтверждения перед внедрением (см. [CLAUDE.md](CLAUDE.md)).

> Визуальная схема (mermaid-диаграммы + сводка решений по каждому слою) опубликована как отдельный артефакт: _AMOLIE — System Architecture_. Этот документ — источник истины с полным обоснованием; артефакт — навигационная витрина по нему.

## 1. Принципы

- Clean Architecture: разделение на слои Domain → Application → Infrastructure → Presentation.
- Feature-Based структура: код группируется по бизнес-возможностям (booking, scheduling, payments), а не по техническому типу файла.
- Каждый модуль независим: явные границы, коммуникация через публичные интерфейсы модуля, без прямых обращений к внутренним деталям соседних модулей.
- Строгая типизация на всех уровнях (TypeScript `strict: true`, без `any`).
- Небольшие файлы и функции с единственной ответственностью (SRP).
- Инфраструктура (БД, платежи, SMS) — заменяемые адаптеры за интерфейсами (Dependency Inversion), чтобы не привязываться намертво к вендору.
- Главный продуктовый принцип, который проверяет каждое архитектурное решение: **онлайн-запись должна оставаться максимально простой** — минимум шагов, минимум задержек, минимум того, что может сломаться между "хочу записаться" и "записался".

### 2a. Что из стека реально подключено

Таблица выше — целевой стек. Сегодня работают: Next.js, Tailwind, TanStack Query,
NestJS, PostgreSQL (Supabase), Drizzle, JWT, Supabase Storage (§7), Resend (§9),
Web Push, Vercel (веб) и Fly.io (API, с 2026-08-12), GitHub Actions.

Sentry подключён с 2026-09-02 (веб и API, европейский регион): отчёты об
ошибках с вычисткой секретов и персональных данных, см. `sentry-scrub.ts` в
ядре. Не подключено: Redis (§13), Stripe, провайдер SMS (§8), OpenTelemetry
(§16). Zustand не понадобился — серверного состояния через TanStack
Query и локального `useState` пока хватает.

**Почта покрывает и аккаунт, и визиты (с 2026-09-01).** Resend отправляет письма
аккаунта (приветствие, подтверждение адреса, сброс пароля), ссылку входа клиента
(§10) и письма о визите — «заявка принята», «подтверждён», «отменён»,
напоминание за сутки. Последние идут через очередь в Postgres (§12), а не прямо
из обработчика: иначе недоступность почтового провайдера роняла бы саму запись.

**Тесты.** До августа 2026 `pnpm test` выполнял `jest --passWithNoTests` и не
проверял ничего. Сейчас: Jest в `apps/api` (217 тестов), Vitest в `apps/web` и
`packages/shared-kernel`. Тесты покрывают доменные правила — жизненный цикл
статусов, политику отмены, разбор адреса записи, сборку `.ics` — и поведение
экранов, где ошибка стоит визита. Облик проверяется прогоном в браузере через
CDP: контраст считается по фактически скомпонованной поверхности, зоны нажатия —
с учётом псевдоэлементов.

## 3. Поддомены и мультиарендность

Центральное архитектурное решение продукта: **каждая организация получает `{username}.amolie.com`** — это её полная публичная витрина (страница записи) и приватный кабинет (`/dashboard`) под одним и тем же, легко произносимым и запоминаемым адресом.

### 3.1. Карта доменов

| Домен                   | Назначение                                                                                                                                                                             |
| ----------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `amolie.com`            | **Сайт-визитка о сервисе** (маркетинг, "как это работает", тарифы) + единая точка входа/регистрации + **кабинет клиента** `/me`. Без публичного каталога мастеров — это не маркетплейс |
| `{username}.amolie.com` | Тенант: публичная страница записи (`/`) + приватный кабинет мастера (`/dashboard/*`, за авторизацией)                                                                                  |
| `api.amolie.com`        | Центральный REST API, общий для всех поддоменов и приложений                                                                                                                           |
| `admin.amolie.com`      | Внутренняя панель команды AMOLIE (`platform_admin`)                                                                                                                                    |

Кабинет клиента (`/me`) стоит на корне, а не под поддоменом мастера, и это то же
решение, прочитанное с другой стороны: у визитов к разным мастерам нет общей
организации, поэтому адрес, принадлежащий одной из них, врал бы о том, чей это
список. Слово `me` зарезервировано в `RESERVED_SLUGS` — мастер с таким адресом
кабинет не заслонит (§3.3).

Один поддомен на организацию — не два разных URL для "визитки" и "кабинета" — упрощает всё: что мастер сообщает клиентам, что индексирует поисковик, что нужно защищать авторизацией (только `/dashboard/*`).

Юридические тексты живут на корне отдельными маршрутами: `/privacy`,
`/terms`, `/cookies`. Все три зарезервированы в `RESERVED_SLUGS` (§3.3) — иначе
статический маршрут перекрыл бы страницу мастера, взявшей такой адрес. Отдельного
динамического сегмента под них нет и быть не может: корневой `[slug]` уже занят
тенантами, и второй динамический сегмент того же уровня Next не допускает —
поэтому три тонких файла над общей фабрикой (`features/legal/page-factory.tsx`).

Содержание документов — данные, а не разметка (`features/legal/documents/`):
одно дерево разделов на язык, один компонент-отрисовщик на все девять сочетаний.
Опись того, что продукт кладёт в устройство посетителя, лежит в
`features/legal/storage-inventory.ts` и служит источником и для таблицы в
политике cookie, и для решения, нужен ли вопрос о согласии. Пока в описи только
строго необходимые записи, согласия не требуется (ст. 5(3) Директивы
2002/58/EC), и посетитель видит уведомление, а не выбор.

Публичный каталог/поиск мастеров (Phase 4 в [ROADMAP.md](ROADMAP.md)) осознанно не размещается на корневом `amolie.com` — этот домен должен оставаться простым сайтом о продукте, а не превращаться в раздел с чужим контентом (профилями мастеров). Точное место каталога (отдельный поддомен, отдельный путь) — открытый вопрос, см. §18.

### 3.2. Резолюция тенанта (routing)

1. Wildcard DNS-запись `*.amolie.com` указывает на edge-сеть хостинга.
2. Wildcard TLS-сертификат выпускается и продлевается автоматически (ACME, DNS-01) — один сертификат покрывает все текущие и будущие поддомены.
3. Edge middleware на каждый запрос читает заголовок `Host`:
   - Если это зарезервированное имя (`www`, `api`, `admin`, ...) → маршрут в соответствующее системное приложение.
   - Иначе `{username}` ищется в кэше (Redis, TTL) → `organization_id` + `status`. Промах кэша → запрос в БД, результат кэшируется.
   - `organization_id` и его статус прокидываются дальше запросом (`X-Org-Id`) — backend никогда сам не парсит `Host`, получает уже готовый контекст.
4. Организация в статусе `suspended`/не найдена → отдельные, оформленные по дизайн-системе страницы ("временно недоступно" / "такого мастера нет"), а не generic 404.

### 3.3. Правила именования `username`

- 3–30 символов, `[a-z0-9-]`, без ведущего/замыкающего дефиса, без повторяющихся дефисов подряд.
- Уникальность регистронезависимая (`citext`/`lower()`-индекс в БД).
- Список зарезервированных имён (системные поддомены + вероятные фишинговые/технические слова: `www, app, api, admin, cdn, static, mail, ftp, my, account, billing, dashboard, help, support, status, docs, blog, staging, dev, test` и т.д.) — проверяется при регистрации, хранится как конфигурация, а не хардкод в одном месте.
- Рекомендация (см. §17, улучшения): базовый фильтр на очевидно оскорбительные/торговые-марки-нарушающие имена перед публичным запуском маркетплейса (Phase 4).

### 3.4. Изоляция данных (multi-tenancy)

- Модель: shared database, shared schema, обязательный `organization_id` на всех тенант-специфичных таблицах.
- Application-слой скоупит каждый запрос текущей организацией — исключает случайный доступ к чужим данным на уровне бизнес-логики.
- Второй рубеж защиты — предложение вынесенное в §17 (Row-Level Security на уровне PostgreSQL).
- При росте отдельных крупных клиентов — schema-per-tenant остаётся опцией на будущее (Phase 5+, не в MVP).

### 3.5. SEO и производительность публичной страницы

- Публичная страница тенанта — статическая генерация + ISR, инвалидация по событию (изменение услуг/расписания/профиля вызывает revalidation через webhook из backend).
- Каждый поддомен — собственные `sitemap.xml`, `robots.txt`, Open Graph и структурированные данные (schema.org `LocalBusiness`/`Service`) — прямой вклад в органическое привлечение клиентов, задел под Phase 4 (маркетплейс).

### 3.6. Вход и редирект на поддомен

Аутентификация — единая для всей платформы, но точка входа одна: форма входа/регистрации на `amolie.com`. Пользователь никогда не подбирает свой поддомен вручную.

1. Пользователь заходит на `amolie.com`, вводит данные для входа (или оставляет заявку на регистрацию — см. §10.1).
2. Backend аутентифицирует, определяет организации, к которым принадлежит пользователь (`organization_members`).
3. Ответ на вход содержит `redirectUrl`:
   - Есть организация → `https://{slug}.amolie.com/dashboard` (мастер/владелец сразу попадает в свой рабочий кабинет).
   - Организации нет (роль `client` в будущей модели единого клиентского аккаунта, см. §17.7) → остаётся на `amolie.com/account`.
4. Refresh-cookie выставлен на домен `.amolie.com` (см. §10), поэтому редирект на поддомен не требует повторного входа — сессия уже валидна.

Пользователь с несколькими организациями (например, управляет двумя салонами) — редирект на последнюю активную/основную организацию, с возможностью переключения внутри кабинета (конкретный UX — уточняется на этапе дизайна дашборда).

## 4. Слои Clean Architecture

```
┌───────────────────────────────────────────┐
│ Presentation  (UI, controllers, DTO)       │  ← зависит от Application
├───────────────────────────────────────────┤
│ Application   (use-cases, оркестрация)     │  ← зависит от Domain
├───────────────────────────────────────────┤
│ Domain        (сущности, бизнес-правила)   │  ← ни от чего не зависит
├───────────────────────────────────────────┤
│ Infrastructure (БД, внешние API, очереди)  │  ← реализует интерфейсы Domain/Application
└───────────────────────────────────────────┘
```

Правило зависимостей: внутренние слои (Domain) не знают о внешних (Infrastructure, Presentation). Infrastructure реализует интерфейсы (порты), определённые в Domain/Application (Ports & Adapters). Пример: модуль `booking` определяет интерфейс `NotificationSender`; конкретная реализация через SMS/Email/Push находится в Infrastructure и подключается через DI — замена провайдера не трогает бизнес-логику.

## 5. Feature-Based структура модулей

```
modules/
  auth/               domain / application / infrastructure / presentation
  organizations/      профиль, публичная страница, дизайн страницы
  onboarding/         первые шаги мастера
  services-catalog/
  scheduling/         публикация окон
  booking/            запись, статусы, отмена клиентом
  client-account/     личность клиента и его визиты поперёк мастеров
  clients/            адресная книга мастера (в границах организации)
  finance/            доход по состоявшимся визитам
  media/              подписанная загрузка в Supabase Storage
  notifications/      письма и web push
  payments/           каркас, Phase 2
  reviews/            каркас, Phase 3
  subscriptions/ platform-settings/ admin-analytics/ health/
shared/               database (schema, drizzle), auth (guards), throttling, validation
packages/shared-kernel/  доменные примитивы: Money, TimeRange, телефон, почта,
                         слаг, локали, темы, коды ошибок, сборка .ics
```

**`clients` и `client-account` — разные вещи, и путать их нельзя.** Первый — это
карточка клиента в CRM мастера, жёстко в границах организации: её заметки, её
история, её блокировка. Второй — аккаунт человека на платформе, один на все
организации. Мастер не должна узнать, что её клиент ходит ещё к кому-то, а клиент
— увидеть, как он у неё записан.

Модули не импортируют внутренние (`infrastructure`/`domain`) детали друг друга напрямую — только публичный `application`-интерфейс. `shared-kernel` — только по-настоящему кросс-модульные примитивы, не "мусорная корзина".

## 6. Booking Engine: защита от гонок

**Продуктовое решение MVP (см. PRD.md §7.4, DATABASE.md §3.8):** доступность — не вычисляемые интервалы времени, а конечный список `published_slots`, которые мастер публикует вручную. Это заметно упрощает защиту от гонок по сравнению с классической моделью "рабочие часы + пересечение диапазонов":

- Создание записи — атомарный conditional update: `UPDATE published_slots SET status = 'booked' WHERE id = ANY($1) AND status = 'available'`. Визит занимает **все** окна, которые покрывает по времени, а не только стартовое: окна не хранят длительность, поэтому двухчасовая запись иначе оставляла бы окна под собой в продаже. Если обновилось меньше строк, чем окон в интервале, значит часть времени уже занята — вся транзакция откатывается. Гонка обработана без exclusion constraint над временными диапазонами.
- Занятость живёт в `booking_slots` с частичным уникальным индексом `unique (published_slot_id) where released_at is null`: невозможность двойной записи гарантирована базой, а не только кодом приложения. Отмена ставит `released_at` вместо удаления строки — история того, что держал отменённый визит, сохраняется.
- Отмена записи — обратный переход `booked → available` в той же транзакции, что и смена статуса записи. Какие статусы освобождают окна, решает `STATUSES_RELEASING_SLOTS` в домене записи — обе отмены, но не `no_show`; список обязан совпадать с предикатом частичного индекса `bookings_active_published_slot_id_unique`, иначе окно свободно в базе и занято в календаре.
- **Принятое ограничение: пропуск в расписании ничего не блокирует.** Проверка «помещается ли визит» смотрит только на уже занятые окна мастера внутри интервала, но не требует, чтобы интервал был покрыт опубликованными окнами целиком. Мастер, свободная в 10:00 всего полчаса, всё равно будет предложена как старт визита на полтора часа — а длительность выбирает клиент, не она. Ответить на этот вопрос иначе нельзя, пока окно не несёт длительности: нужен либо шаг сетки у салона (`organizations.slot_step_minutes`), либо явный конец у окна. Оба варианта — изменение схемы; до тех пор это поведение, а не дефект. См. комментарий у `listAvailableFittingDuration`.
- Идемпотентность на уровне API: `Idempotency-Key`, повторный запрос не создаёт дубль.
- Короткоживущий soft-hold слота в Redis на время прохождения шагов оплаты, с TTL.

## 6a. Как гость узнаёт решение мастера

Писем о записях продукт не шлёт (§9), поэтому связь с гостем держится на двух
вещах, ни одна из которых ничего не стоит в эксплуатации:

- **`bookings.public_token`** и публичная страница `/{slug}/booking/{token}`.
  Токен — ключ человека к собственной записи в тот момент, когда аккаунта у него
  ещё нет: записываются гостем, и опознать вернувшегося больше нечем (аккаунт
  предлагается после записи, см. §6a.1). Экран подтверждения показывает
  ссылку только когда ждать действительно есть чего: при включённом
  авто-подтверждении ждать нечего.
- **Календарный файл** `/{slug}/booking/{token}/calendar.ics` с будильником за
  два часа. Это единственное напоминание, которое продукт способен дать без
  единого провайдера, и оно приходит на телефон с закрытым приложением.

Файл отдаёт **маршрут Next**, а не API: ссылка должна быть обычным адресом,
который человек может нажать и переслать, а BFF-прокси (§11) пробрасывает только
`Content-Type` — `Content-Disposition` потерялся бы. Отдаётся `inline`, а не
`attachment`: `attachment` — прямая инструкция сохранить файл, и iOS ей
подчиняется, укладывая визит в «Файлы» вместо «Календаря».

Сборка `.ics` — чистая функция в `shared-kernel` (`calendar.ts`), покрытая
тестами: экранирование запятых и точек с запятой и сворачивание строк **по
байтам** (кириллица занимает два, и счёт по символам пропускал бы строки почти
вдвое длиннее лимита RFC 5545) — ровно те места, где такие файлы ломаются.

### 6a.1. Аккаунт появляется после записи, а не до неё

Записаться по-прежнему можно гостем: аккаунт — не условие записи, а то, что
предлагается после неё («сохранить эту запись за собой»). Обменяв секретную
ссылку на подтверждённый адрес почты, человек получает `amolie.com/me` —
**один список визитов ко всем мастерам сразу**, вместо ссылки на каждую запись.

Разделены две сущности, которые легко спутать: `users` — человек на платформе,
`clients` — его карточка в CRM конкретного мастера (§5). Склейка прошлых записей
с аккаунтом происходит только по доказанному владению почтой; совпадение телефона
доказательством не считается — его вписывают с ошибкой и вписывают чужой, а
склеенные по нему записи показали бы одному человеку визиты другого.

Отменить визит клиент может сам, если мастер это разрешила
(`organizations.client_cancellation_hours`, см. [API.md](API.md) §6.7b). Правило
принадлежит мастеру и одно на оба входа — гостя по токену и вошедшего клиента.

## 6b. Языки интерфейса

Три языка — русский, латышский, английский — **без `next-intl` и без сегмента
`[locale]` в URL**. Причина продуктовая: каждая ссылка, которую продукт когда-либо
печатал, выглядит как `amolie.com/{slug}`, и страница мастера живёт у неё в шапке
инстаграма. Переезд на `/ru/{slug}` сломал бы эти ссылки ради выгоды, которой
никто не просил: язык страницы — свойство её владельца, а не адреса.

- **Два независимых языка.** `users.locale` — язык кабинета, `organizations.default_locale`
  — язык публичной страницы. Рижский мастер вполне может вести кабинет по-русски,
  показывая страницу по-латышски.
- **Словарь типизирован по русскому** (`apps/web/src/lib/i18n/`): ключи берутся из
  `ru`, значения расширяются до `string`. Без расширения `as const` сделал бы
  каждое значение собственным литеральным типом, и перевод не мог бы отличаться от
  оригинала. Недопереведённый ключ показывает русский, а не `bookings.groupPending`.
- **Не переводится то, что написала мастер**: названия и описания услуг, её
  описание, отображаемое имя, заметки о клиентах.
- **Грамматику считает `Intl`**: формы множественного числа через `Intl.PluralRules`
  (в русском три, в латышском свои три, в английском две), дни недели и месяцы —
  через `Intl.DateTimeFormat`.
- **`getMessages` живёт вне клиентского модуля.** Реэкспорт из файла с `'use client'`
  превращает функцию в клиентскую ссылку, которую сервер вызвать не может.
  Серверная локаль резолвится через `getRequestLocale` в React `cache`, чтобы
  layout и страница не делали по своему запросу `/auth/me` на каждый рендер.

## 7. Storage (медиа) — **реализовано**

- Supabase Storage: фото профиля, обложка, фон страницы, снимки работ.
- Загрузка идёт **напрямую из браузера** по подписанной ссылке, которую выдаёт
  `media`-модуль; бинарные данные через API не проходят. Ключ сервисной роли
  живёт только на сервере.
- Путь объекта строится в домене (`media-object-path.ts`) и всегда начинается с
  идентификатора организации: чужую папку подписанная ссылка адресовать не может.
- Тип и размер файла проверяются до выдачи подписи (`shared-kernel/media-upload`).
- Чего нет: CDN с несколькими размерами (отдаётся оригинал) и антивирусной
  проверки. Ссылкой изображение задать по-прежнему можно — это осталось как
  запасной путь, а не как единственный.

## 8. SMS — **не реализовано**

Ниже — план. Ни одного провайдера не подключено, ни одно сообщение не
отправляется.

**Упирается не в код.** Чтобы отправлять с именем отправителя (`AMOLIE`, а не с
номера), в каждой стране нужна отдельная регистрация A2P-сендера с документами
компании, и правила у Латвии, Литвы, Польши, Германии разные. Пока юридического
лица нет, канал закрыт целиком; когда появится — открывается по одной стране за
раз. То же самое у WhatsApp Business API: Meta требует верификации бизнеса.

- Провайдер с реальным покрытием и приемлемой доставляемостью в Латвии/Балтии — финальный выбор фиксируется отдельно.
- Интерфейс `SmsSender` в Domain/Application, конкретный провайдер — в Infrastructure (Ports & Adapters, см. §4). Позволяет добавить резервного провайдера без изменений в модуле `notifications`.
- SMS — основной канал напоминаний (наибольшее влияние на снижение no-show, см. [PRD.md](PRD.md) §10), поэтому доставляемость этого канала мониторится отдельно (см. §16).

## 9. Email — **реализовано**

Подключён Resend: транзакционный API вместо своего SMTP — доставляемость важнее
контроля инфраструктуры. Тексты живут в API (`notifications/letters.ts`) на трёх
языках и версионируются вместе с кодом: письмо отправляет сервер, и тащить сюда
словарь фронтенда значило бы связать сервер со сборкой веба.

**Письма аккаунта** — приветствие мастеру, подтверждение адреса, сброс пароля,
ссылка входа клиента (§10) — уходят прямо из обработчика. Отправка не блокирует
действие, которое её вызвала, и ошибки проглатываются с записью в лог:
недоступный почтовый провайдер не может отменить уже созданный аккаунт.

**Письма о визите** — «заявка принята», «визит подтверждён», «визит отменён»,
напоминание за сутки — уходят **через очередь** (§12), и это разница не в
удобстве, а в надёжности: у писем аккаунта есть замена (кнопка «забыли
пароль»), а у клиента, не получившего подтверждения, замены нет — он просто не
знает, ждут его или нет. Очередь даёт повторы, а `run_at` — само напоминание.
Тексты живут отдельным словарём (`notifications/booking-letters.ts`): у писем
аккаунта адресат мастер и язык из `users.locale`, у писем о визите адресат тот,
кто записался, чаще всего без аккаунта вовсе, и язык берётся из его кабинета,
если аккаунт есть, иначе из языка страницы, на которой он записывался.

Кому не пишем: клиенту, отменившему визит самому (он только что нажал кнопку и
увидел результат), и клиенту, которого мастер завела в календарь руками — он
ничего не просил.

**Чего нет:** запроса отзыва после визита (Phase 3). Ключ провайдера
отсутствует в разработке намеренно — письмо тогда печатается в лог целиком, и
ссылку видно без почтового ящика.

## 10. Authentication

- **Мастер и админ — пароль.** JWT access-токен в httpOnly-куке, которую ставит
  Next-BFF: сырой токен никогда не попадает в браузерный JS. Ротации refresh нет
  — вместо неё `users.token_version`: каждый токен несёт поколение, под которым
  подписан, и смена пароля поднимает счётчик, разом закрывая все открытые сессии.
  Без этого «кто-то знает мой пароль» решалось бы только ожиданием, пока токен
  протухнет сам.
- **Клиент — ссылка из письма, без пароля.** Он заходит несколько раз в год, и
  пароль, заведённый ради такого, будет либо забыт, либо повторён с чужого сайта.
  Ссылка живёт час и срабатывает один раз (`user_tokens`, purpose
  `client_sign_in`); в базе хранится её SHA-256, а не она сама. Гасится ссылка
  `POST`-запросом из уже открытой страницы, а не переходом по `GET`: почтовые
  сканеры ходят по ссылкам заранее и сожгли бы одноразовый вход до человека.
- **Мастеру и админу ссылка входа не выдаётся.** Письмо «войдите одним нажатием»
  открывало бы полный доступ к чужому бизнесу тому, кто добрался до почтового
  ящика, — не спрашивая даже старого пароля.
- Домен cookie — `.amolie.com` (родительский), чтобы сессия была валидна при
  переходах между поддоменами: это нужно и `platform_admin`, и клиенту, чей
  кабинет живёт на корне, а страницы мастеров переедут на поддомены (§3).
- Ролевая модель: `client`, `master`, `salon_admin`/`owner`, `platform_admin`.
- OTP по телефону — когда появится SMS (§8).

### 10.1. Регистрация мастеров по заявке

На старте регистрация мастеров/салонов — **модерируемая**. Это осознанное решение: на раннем этапе важнее качество онбординга и контроль над тем, кто выходит на платформу, чем скорость роста числа аккаунтов.

- Режим хранится настройкой `platform_settings.registration_mode`: `moderated` (по умолчанию) или `open`. Переход к открытой регистрации — решение владельца продукта, а не деплой.
- Мастер приходит на `amolie.com/register`, заполняет форму (имя, почта, телефон, язык, пароль и рассказ о себе) и отправляет **заявку**. Пароль хешируется argon2 сразу и хранится в заявке до решения.
- Администраторы платформы получают push-уведомление (`/admin` — устанавливаемое PWA) и видят заявку в очереди `/admin/registration-requests`.
- Одобрение одной транзакцией создаёт `users` (роль `master`) → `organizations` (`slug` выводится из имени, см. §3.3) → `organization_members` (роль `owner`), после чего хеш пароля из заявки удаляется, а мастеру уходит письмо «входите тем же паролем».
- **Адрес, за которым уже стоит аккаунт клиента, ведёт к повышению, а не к отказу.** Человек, который записывался к мастеру, а потом сам пришёл на платформу, — тот же человек: второго аккаунта на ту же почту не бывает, и его история записей должна остаться при нём. Одобрение в этом случае не заводит `users`, а выдаёт одноразовую ссылку (`user_tokens.purpose = 'master_upgrade'`) и отправляет её на сам адрес; кабинет открывается по переходу (`POST /auth/registration/confirm-upgrade`), который и превращает аккаунт в мастерский, ставит пароль из заявки, создаёт салон и сразу выдаёт сессию.
  Через письмо, а не сразу: адрес при подаче заявки не проверяется, и заявку с чужим адресом отправляет кто угодно — мгновенное повышение отдало бы заявителю чужой аккаунт вместе с историей. До подтверждения заявка числится одобренной с пустым `created_user_id`, и панель показывает её как «Ждёт подтверждения». Аккаунт мастера или администратора на том же адресе не повышается никогда: что делать с двумя мастерами на один адрес — решение человека, а не правило (`409`, код `registration_email_is_master`).
- **Одобрение не подтверждает адрес — его подтверждает переход по ссылке.** Заведённому аккаунту вслед за письмом «входите тем же паролем» уходит второе, со ссылкой `/verify-email` (`user_tokens.purpose = 'email_verification'`, сутки), и до перехода `users.email_verified_at` остаётся пустым. Одобрение администратором доказательством не считается: адрес человек вписал сам и пароль задал тогда же, а администратор ручается за то, что заявка настоящая, а не за то, что почта не чужая. Повышение существующего клиента подтверждения не требует — он уже переходил по ссылке на этот адрес, и `email_verified_at` ставится сразу. Токен выпускается с ожиданием, письмо уходит без него: невыпущенный токен взять неоткуда, а неушедшую ссылку человек получит заново.
- Отказ обязателен с причиной; она уходит письмом. Отказ не блокирует адрес — человек может подать заявку снова.
- Одна открытая заявка на адрес (частичный уникальный индекс). Повторная → `409` с кодом `registration_pending`.
- В режиме `open` та же форма создаёт аккаунт немедленно и возвращает токены; очередь не задействуется.

Инвайт-коды (прежний механизм закрытой регистрации) удалены вместе с таблицей `invite_codes` — см. [CHANGELOG.md](CHANGELOG.md).

## 12. Background Jobs и Queues — **реализовано на Postgres**

**Очередь живёт в той же базе (таблица `jobs`, DATABASE.md §3.14), воркер — в
процессе API.** BullMQ поверх Redis, стоявший здесь как план, отвергнут при
реализации (решение владельца, 2026-09-01): очередь на десяток писем в час не
стоит отдельного сервиса — новой инфраструктуры, новых денег и ещё одной точки
отказа. pg-boss отвергнут по другой причине: он рассчитан на сессионные
соединения и `LISTEN/NOTIFY`, а API ходит в базу через пулер Supabase.

Как устроено:

- **Выборка** — `UPDATE ... WHERE id IN (SELECT ... FOR UPDATE SKIP LOCKED)`
  одним оператором. Две машины, спросившие одновременно, разбирают разные
  строки; между «выбрали» и «пометили» нет промежутка, в котором клиент получил
  бы второе письмо. Единственный запрос проекта, который обязан быть собран
  шаблоном `sql`, — и потому проверяется против живого Postgres.
- **Отложенность** — колонка `run_at`. Напоминание за N часов это задача с
  датой в будущем, а не отдельный планировщик.
- **Повторы** — экспоненциальная отсрочка (30 с × 2ⁿ, потолок 30 мин),
  `max_attempts` по умолчанию 5, исчерпавшая попытки уходит в `failed` и
  остаётся в таблице: письмо, которое так и не ушло, обязано оставить след.
  Число мёртвых задач видно на экране «Состояние платформы».
- **Смерть машины** — задача, взятая больше пятнадцати минут назад, возвращается
  в очередь. Счётчик попыток уже увеличен, поэтому вечного круга нет.
- **Отсутствие двойников** — `dedupe_key` с частичной уникальностью среди живых
  задач: напоминание о визите ровно одно, сколько бы раз запись ни правили.
- **Кто что исполняет** — реестр обработчиков (`JobHandlersRegistry`), а не
  `switch` в воркере: очередь общая, а письма о записях принадлежат
  уведомлениям.

Опрос раз в пять секунд, пачка из пяти задач. `JOBS_WORKER_ENABLED=false`
выключает разбор в этом процессе — день, когда воркер отделится в свою машину,
будет стоить смены флага.

Целевой каталог задач (реализованы письма о записях и напоминание; остальное —
план):

| Задача                             | Триггер                       | Особенность                                                        |
| ---------------------------------- | ----------------------------- | ------------------------------------------------------------------ |
| Напоминание о записи               | Подтверждение записи мастером | **Сделано.** Задача с `run_at` на T-24ч; снимается при отмене      |
| Письмо о визите (email)            | События модуля записей        | **Сделано.** Ретраи с экспоненциальной отсрочкой, dead-letter      |
| Обработка загруженного изображения | Загрузка фото в `storage`     | Генерация responsive-вариантов                                     |
| Ретраи вебхуков (Stripe)           | Ошибка обработки вебхука      | Идемпотентно по `event.id`                                         |
| Проверка подписок платформы        | Расписание (cron)             | Обновление статуса `subscriptions`, уведомление при `past_due`     |
| GDPR-экспорт/удаление данных       | Запрос пользователя           | Асинхронно, т.к. может требовать сбора данных из нескольких таблиц |
| Запрос отзыва после визита         | Отметка `completed` (Phase 3) | Отложенная джоба через N часов после визита                        |

Очередь — не только «фоновая работа», но и механизм надёжности: at-least-once
доставка, явные ретраи, dead-letter вместо тихой потери события. At-least-once
означает, что обработчик обязан быть идемпотентным: задачу можно взять повторно
после упавшей машины.

## 13. Caching

| Кэш                            | Слой                                 | TTL/инвалидация                                            |
| ------------------------------ | ------------------------------------ | ---------------------------------------------------------- |
| `username → organization_id`   | Redis, читается на edge/в middleware | TTL + явная инвалидация при смене slug/статуса организации |
| Доступные слоты (availability) | Redis                                | Короткий TTL + инвалидация при создании/отмене записи      |
| Rate-limit счётчики            | Redis                                | Скользящее окно                                            |
| Публичная страница тенанта     | Edge/ISR (CDN)                       | On-demand revalidation по webhook из backend               |

Кэш доступности — не источник истины (истина всегда в Postgres с exclusion constraint), а ускоритель чтения с явным механизмом инвалидации, чтобы никогда не показать клиенту слот, который на самом деле уже занят.

## 14. Масштабируемость

- Stateless backend-инстансы — горизонтальное масштабирование за балансировщиком.
- Публичные страницы — статика/ISR/edge-кэш, инвалидация точечная.
- Тяжёлые/асинхронные операции — в очередь, не блокируют пользовательский запрос.
- Read-replica БД — кандидат при росте нагрузки на аналитику/отчётность (Phase 5+, не в MVP).

## 15. Безопасность

- AuthN/AuthZ — см. §10; RBAC-проверка на каждый use-case в Application-слое.
- Tenant isolation — `organization_id` в каждом запросе (см. §3.4) + предложение усилить Row-Level Security (см. §17).
- WAF/DDoS-защита перед wildcard-доменом — большая площадь поддоменов сама по себе привлекает автоматическое сканирование, это увеличивает, а не уменьшает потребность в защите на edge.
- Предотвращение subdomain takeover: поддомены — исключительно first-party (не CNAME на внешние сервисы), Host-заголовок валидируется против известного паттерна/списка организаций, никаких "висящих" DNS-записей на внешние ресурсы.
- Секреты — только через секрет-менеджер хостинг-провайдера, никогда в репозитории.
- Валидация всех входных данных на границе (Presentation layer).
- Аудит критичных действий (`audit_log`) — создание/отмена записи, изменение платёжных настроек, изменение роли участника.
- Регулярное сканирование зависимостей (Dependabot/Snyk-класс инструмент).

## 16. Monitoring и Logging

- **Ошибки:** Sentry (или аналог) — фиксация необработанных исключений на frontend и backend с полным стектрейсом и контекстом (без PII в открытом виде).
- **Трассировка:** OpenTelemetry как вендоронезависимый стандарт инструментирования — один `trace_id` прослеживает запрос от edge middleware через backend-модуль до фоновой задачи в очереди. Экспортируется в выбранный backend наблюдаемости (напр. Grafana Cloud/Better Stack), что не привязывает продукт к одному APM-вендору.
- **Логи:** структурированные JSON-логи с обязательными полями `trace_id`, `organization_id`, `user_id` (если есть) — это то, что превращает разбор инцидента у конкретного мастера из ручного поиска в один фильтр по `organization_id`. Персональные данные (телефон, email, содержимое SMS) в логи не пишутся в открытом виде.
- **Бизнес-метрики:** число созданных записей, конверсия публичной страницы, no-show rate — отдельный дашборд, связан с модулем Admin/Analytics (Phase 3, см. [PRD.md](PRD.md) §10).
- **Health-check:** отдельный лёгкий эндпоинт (проверка доступности БД/Redis), используется внешним uptime-мониторингом и хостинг-провайдером при rolling-деплое (см. [DEPLOYMENT.md](DEPLOYMENT.md) §7).
- **Алертинг:** отдельно отслеживается доставляемость SMS/email (см. §8–9) — недоставленное напоминание напрямую бьёт по ключевой метрике продукта (no-show rate), поэтому это не просто "ещё один лог", а сигнал с приоритетным алертом.

## 17. Предлагаемые улучшения

Сверх базового плана — решения, заметно повышающие качество/снижающие риск при небольшой дополнительной сложности. Каждое — отдельное решение, ожидающее подтверждения.

1. **Cloudflare R2 вместо классического S3** — S3-совместимый API, но без платы за исходящий трафик; заметная экономия при раздаче фото мастеров/услуг на мобильный трафик по мере роста.
2. **Row-Level Security в PostgreSQL** — второй, независимый от кода backend, рубеж мультитенантной изоляции: даже баг в бизнес-логике не даст СУБД отдать чужие данные.
3. **Passkeys (WebAuthn) для владельцев организаций** — аккаунт мастера даёт доступ к выплатам и данным клиентов, это высокоценная цель; passkeys устойчивы к фишингу и удобнее пароля на мобильном.
4. **react-email для email-шаблонов** — типизированные компоненты вместо HTML-строк, проще поддерживать на трёх языках и тестировать превью.
5. **Собственные домены для тарифов Pro/Business (Phase 5+)** — салон подключает свой домен через CNAME, SSL выпускается автоматически (Cloudflare for SaaS-класс решение); стандартная монетизируемая опция для этого класса SaaS.
6. **Резолюция поддомена на самом edge (Cloudflare Worker)** — несуществующий/неактивный поддомен получает ответ ещё до обращения к frontend-серверу; снижает нагрузку от паразитного трафика сканеров по wildcard-домену.
7. ~~**Единый аккаунт клиента поверх всех поддоменов**~~ — **сделано** (август 2026): аккаунт один на платформу, кабинет на `amolie.com/me`, карточки клиента в CRM мастеров остались раздельными. Решение принято до Phase 4 именно затем, чтобы не переделывать его вместе с маркетплейсом: слияние заведённых порознь аккаунтов — миграция с ручным разбором конфликтов.
