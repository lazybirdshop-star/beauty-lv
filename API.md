# API — AMOLIE

Версия 0.3 (черновик для утверждения). Стиль API: **REST** (предложение — см. §9 об альтернативах).

## 1. Общие принципы

- Базовый путь: `/api/v1`. Версионирование через префикс пути.
- Формат данных: JSON (`Content-Type: application/json`), UTF-8.
- Все временные метки — ISO 8601 в UTC (`2026-07-30T14:00:00Z`). Разворачивает
  их клиент — но **в пояс организации**, а не устройства: окно, открытое
  мастером на 14:00, читается как 14:00 и у клиента из другой страны, потому
  что придёт он именно тогда. Пояс приезжает в ответе (`organizations.timezone`
  — публичный профиль §6.1, визиты кабинета клиента §11).
- Деньги в ответах API передаются как объект `{ amount: number (в центах), currency: string }`, никогда как float в валюте.
- Идентификаторы — UUID-строки.
- Аутентификация: `Authorization: Bearer <access_token>`.
- Мультиарендность: контекст организации определяется из токена/пути, клиент не может передать произвольный `organization_id` для чтения чужих данных.

## 2. Аутентификация и авторизация

### 2.1. Формат токенов

- `access_token` — JWT, TTL 15 минут, передаётся в заголовке.
- `refresh_token` — httpOnly secure cookie, TTL 30 дней, используется только эндпоинтом обновления токена.

### 2.2. Эндпоинты

| Метод | Путь                                 | Описание                                                                                                                                      |
| ----- | ------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------- |
| POST  | `/auth/register`                     | Регистрация мастера/организации. В режиме `moderated` создаёт заявку, в `open` — сразу аккаунт (см. [ARCHITECTURE.md](ARCHITECTURE.md) §10.1) |
| POST  | `/auth/registration/confirm-upgrade` | «Стать мастером» по ссылке из письма об одобрении: клиентский аккаунт становится мастерским и сразу получает сессию                           |
| GET   | `/auth/registration-mode`            | Как платформа впускает сегодня: `moderated` или `open`. Без авторизации                                                                       |
| POST  | `/auth/login`                        | Вход по паролю. Ответ включает `redirectUrl` (см. ниже)                                                                                       |
| POST  | `/auth/otp/request`                  | Запрос одноразового кода на телефон/email                                                                                                     |
| POST  | `/auth/otp/verify`                   | Подтверждение OTP → выдача токенов                                                                                                            |
| POST  | `/auth/refresh`                      | Обновление access-токена по refresh-токену                                                                                                    |
| POST  | `/auth/logout`                       | Инвалидация refresh-токена                                                                                                                    |
| POST  | `/auth/password/forgot`              | Запрос сброса пароля                                                                                                                          |
| POST  | `/auth/password/reset`               | Установка нового пароля по токену сброса                                                                                                      |

Пример `POST /auth/register`:

```json
{
  "fullName": "Anna Bērziņa",
  "email": "anna@example.com",
  "phone": "+37120000000",
  "locale": "lv",
  "password": "...",
  "message": "Маникюр и педикюр, работаю в Риге, @anna.nails"
}
```

Ответ размечен режимом платформы, а не угадывается по полям:

```json
{ "mode": "moderated", "requestId": "…" }
```

В режиме `open` ответ тот же, что у `/auth/login`, плюс `"mode": "open"` — мастер уже авторизована в только что созданной организации.

Заявка с адреса, который уже стоит в очереди, → `409` с кодом `registration_pending`; занятый email/телефон → `409` с `email_taken`/`phone_taken`.

Пример ответа `POST /auth/login`:

```json
{
  "accessToken": "...",
  "user": { "id": "uuid", "fullName": "Anna Bērziņa", "role": "master" },
  "redirectUrl": "https://anna-nails.amolie.com/dashboard"
}
```

`redirectUrl` вычисляется backend'ом по правилам из [ARCHITECTURE.md](ARCHITECTURE.md) §3.6: есть организация → её поддомен; нет — остаётся `null` (пользователь остаётся на `amolie.com`).

### 2.3. Роли и доступ

Проверка прав — на уровне Application-слоя backend (см. [ARCHITECTURE.md](ARCHITECTURE.md) §15). Общая матрица:

| Роль             | Доступ                                                                                            |
| ---------------- | ------------------------------------------------------------------------------------------------- |
| `client`         | Свои записи, свой профиль, публичные данные организаций                                           |
| `master`         | Данные своей организации: расписание, записи, услуги (в рамках прав, назначенных `admin`/`owner`) |
| `admin`/`owner`  | Полное управление организацией, сотрудниками, биллингом                                           |
| `platform_admin` | Административные эндпоинты `/admin/*`, доступ ко всем организациям                                |

## 3. Формат ошибок

Единый формат на основе RFC 7807 (Problem Details):

```json
{
  "type": "https://amolie.com/errors/booking-slot-unavailable",
  "title": "Slot is no longer available",
  "status": 409,
  "detail": "Выбранный слот был занят другим клиентом.",
  "instance": "/api/v1/bookings",
  "traceId": "a1b2c3d4"
}
```

Коды состояния:

- `400` — некорректный запрос (валидация).
- `401` — не аутентифицирован.
- `403` — нет прав.
- `404` — сущность не найдена.
- `409` — конфликт (напр. слот занят, дублирующийся email).
- `422` — семантически некорректные данные.
- `429` — превышен rate limit.
- `500` — внутренняя ошибка.

## 4. Пагинация, фильтрация, сортировка

- Пагинация — курсорная для лент (записи, уведомления): `?cursor=<opaque>&limit=20`.
- Ответ со списком:

```json
{
  "data": [/* ... */],
  "meta": { "nextCursor": "opaque-string-or-null" }
}
```

- Фильтрация — явные query-параметры (`?status=confirmed&from=2026-08-01&to=2026-08-07`), без свободного query-языка в MVP.
- Сортировка — `?sort=starts_at:asc`.

## 5. Идемпотентность

Все небезопасные операции создания критичных сущностей (`POST /bookings`, `POST /payments`) принимают заголовок `Idempotency-Key`. Повторный запрос с тем же ключом в течение 24 часов возвращает результат первого выполнения без повторного создания сущности.

## 6. Ключевые группы эндпоинтов

**Этот раздел описывает то, что действительно есть в коде.** Пути, отличающиеся
от первоначального плана, отличаются осознанно: master-facing CRUD живёт под
`/organizations/{slug}/...` (не `/organizations/me/...` — `OrgMembershipGuard`
резолвит организацию из `:slug`), а публичные эндпоинты помечены префиксом
`public-`, потому что путь без префикса уже занят guarded-контроллером той же
сущности, и два контроллера не могут владеть одним путём.

Разделы 6.5–6.7 — планируемое; они помечены явно.

### 6.1. Organizations & Profile

| Метод | Путь                            | Авторизация | Описание                                                       |
| ----- | ------------------------------- | ----------- | -------------------------------------------------------------- |
| GET   | `/organizations/me`             | JWT         | Организация текущего пользователя                              |
| GET   | `/organizations/me/summary`     | JWT         | Сводка для главной кабинета: ближайшие, клиенты, доход, лента  |
| PATCH | `/organizations/{slug}/profile` | JWT + права | Профиль и оформление публичной страницы (частичное обновление) |
| GET   | `/organizations/{slug}`         | —           | Публичный профиль для страницы записи                          |

`PATCH .../profile` принимает любое подмножество полей. Экраны кабинета
пользуются этим: переключатель авто-подтверждения в разделе «Записи» шлёт одно
поле, а не всю форму страницы — PATCH, несущий неотредактированные описание и
контакты, способен затереть их по случайности.

`GET /organizations/{slug}` отдаёт и `timezone` — сутки салона. Публичная
страница без него не может назвать час: моменты приходят в UTC, а
`getHours()` на сервере отрисовки и в браузере посетителя дают три разных
времени для одного окна.

`designPresetKey` — единственное поле профиля с проверкой права, а не только
формата: мир вне предложения каталога принимается лишь у той организации,
которой он выдан (`custom_design_key`), иначе `403`
([DESIGN_STUDIO.md](DESIGN_STUDIO.md) §7.4a).

Локации и сотрудники (`/members`, `/locations`) в MVP не реализованы: продукт
рассчитан на одиночного мастера (PRD.md §2).

#### Публичный адрес страницы

| Метод | Путь                                                       | Авторизация                 | Описание                                                      |
| ----- | ---------------------------------------------------------- | --------------------------- | ------------------------------------------------------------- |
| GET   | `/organizations/{slug}/public-address/availability?value=` | JWT + `org:settings:manage` | Свободен ли адрес; отвечает причиной                          |
| PATCH | `/organizations/{slug}/public-address`                     | JWT + `org:settings:manage` | Сменить адрес страницы                                        |
| POST  | `/organizations/{slug}/public-address/keep`                | JWT + `org:settings:manage` | «Оставляю этот» — отметить адрес выбранным без переименования |

Адрес намеренно вынесен из `PATCH .../profile`: это не поле профиля, а
идентификатор, который держат в руках другие люди. Смена переносит каждую
ссылку, что мастер раздала, поэтому у операции свои правила — валидация против
`shared-kernel` (`validatePublicSlug`: длина, формат, список зарезервированных
платформой слов), проверка занятости, лимит 3 смены за 30 дней и запись
прежнего адреса в историю. Право `org:settings:manage` (владелец), а не
`org:profile-page:manage`: администратор салона, которому можно переписать
страницу, не должен иметь возможности её **перенести**.

`GET .../availability` отвечает 200 всегда, даже когда адрес не годится:
поле спрашивает на каждом нажатии клавиши, и интерфейс, которому нужно поймать
исключение, чтобы показать подсказку, краснеет раньше, чем мастер дописала
второй символ. Форма ответа: `{ slug, available, reason, current }`, где
`reason` — код (`too-short` | `too-long` | `format` | `reserved` | `taken`),
а слова подбирает панель на языке мастера. `PATCH` при отказе отвечает 409 с
тем же кодом в поле `reason` (плюс `too-many-changes`).

Прежний адрес продолжает работать: `GET /organizations/{slug}` для него
отвечает 404 с полем `movedTo` — текущим адресом организации, — а публичная
страница превращает это в 308 (см. `organization_slug_history` в
[DATABASE.md](DATABASE.md) §3.2a).

#### Онбординг — пошаговая настройка кабинета

| Метод | Путь                   | Авторизация | Описание                                       |
| ----- | ---------------------- | ----------- | ---------------------------------------------- |
| GET   | `/onboarding`          | JWT         | Состояние настройки: шаги, прогресс, следующий |
| POST  | `/onboarding/complete` | JWT         | «Готово» — идемпотентно                        |
| POST  | `/onboarding/restart`  | JWT         | Пройти настройку заново                        |

Верхнеуровневый путь, а не `/organizations/...`: контроллер организаций владеет
`:slug`, и каждый добавленный туда маршрут приходится защищать от прочтения как
имени мастера. Организация резолвится из членства — вызывающий её не называет.

Ответ: `{ slug, completedAt, steps: [{ key, done, optional }], nextStep }`.
Шаги — `address`, `profile`, `design`, `services`, `schedule`, `share` —
именно в этом порядке: каждый предыдущий является условием следующего.
**Готовность шага выводится из данных, а не хранится**: сохранённая галочка
«шаг 4 пройден» — утверждение о прошлом, а `serviceCount > 0` — факт о
настоящем, и они расходятся в тот момент, когда мастер удаляет услугу,
созданную при настройке. В базе живёт только `onboarding_completed_at`: «я
закончила с этим экраном» — действительно решение, а не факт о данных.
`share` (первая запись) помечен `optional`: его закрывает клиент, и чек-лист,
который не даёт себя закрыть, пока не сделал кто-то другой, не закрывается
никогда.

#### Design Studio — облик публичной страницы

Контракт режима Студии ([DESIGN_STUDIO.md](DESIGN_STUDIO.md) §7). Все пути
охраняются JWT, членством в организации и правом `org:profile-page:manage`.

| Метод  | Путь                                         | Описание                                                      |
| ------ | -------------------------------------------- | ------------------------------------------------------------- |
| GET    | `/organizations/{slug}/page-design`          | Опубликованное, черновик, признак архива и история публикаций |
| PUT    | `/organizations/{slug}/page-design/draft`    | Автосохранение черновика; на публику не попадает              |
| DELETE | `/organizations/{slug}/page-design/draft`    | «Вернуться к опубликованному» — сброс черновика               |
| POST   | `/organizations/{slug}/page-design/publish`  | Публикация; пустое тело публикует текущий черновик            |
| POST   | `/organizations/{slug}/page-design/rollback` | Откат: новая публикация слепка версии `{version}`             |

Тело — решения мастера по десяти ручкам (`PageDesign` в `shared-kernel`), а не
значения токенов. **Сервер не доверяет клиенту** (§7.4): ключи вне списка
ручек отбрасываются, значения вне каталогов заменяются авторскими, цвета
доводятся автокоррекцией до проходящей норму ступени, производные
(`--accent-contrast`, `--accent-soft`) не принимаются никогда и всегда
выводятся резолвером. Поэтому запрос не отклоняется за «неправильный» цвет —
он сохраняет исправленный: непроходящего в базе не существует.

Прежние поля оформления (`designPresetKey`, `themeOverrides`, `heroStyle`,
`coverUrl`…) остаются в `PATCH .../profile` и синхронизируются публикацией:
пока их читает хоть один потребитель, два представления обязаны быть в
согласии.

### 6.3. Availability (мастер публикует окна вручную)

**Продуктовое решение MVP (PRD.md §7.4):** без рабочих часов и расписания.
`published_slots` — конечный список конкретных окон, опубликованных вручную;
ничего не вычисляется.

| Метод        | Путь                                          | Авторизация | Описание                                               |
| ------------ | --------------------------------------------- | ----------- | ------------------------------------------------------ |
| GET/POST     | `/organizations/{slug}/slots`                 | JWT + права | Свои окна (сужается `?from`/`?to`) и публикация одного |
| POST         | `/organizations/{slug}/slots/bulk`            | JWT + права | Публикация периода: даты × дни недели × шаг            |
| PATCH/DELETE | `/organizations/{slug}/slots/{id}`            | JWT + права | Перенос / удаление свободного окна                     |
| DELETE       | `/organizations/{slug}/slots/bulk`            | JWT + права | Снятие свободных окон за период (`?from`/`?to`)        |
| PATCH        | `/organizations/{slug}/slots/{id}/visibility` | JWT + права | Скрыть окно от клиентов или вернуть его (`{hidden}`)   |
| PATCH        | `/organizations/{slug}/slots/bulk/visibility` | JWT + права | То же периодом (`{from,to,hidden}`)                    |
| GET          | `/organizations/{slug}/public-availability`   | —           | Только `available`; см. `durationMinutes` ниже         |

**Снятие периода — обратная операция к публикации периодом.** Обе границы
обязательны, в отличие от чтения: у списков «ничего не задано» разумно значит
«всё», а у удаления это значило бы «снять вообще всё» в ответ на запрос, где
мастер просто ничего не выбрала.

Занятые окна остаются, и это не ошибка: ответ говорит `removedCount`, чтобы
мастер увидела, что часть времени продана и требует отдельного решения.
`status = 'available'` стоит в самом `WHERE`, а не проверяется заранее — между
проверкой и удалением клиент успел бы записаться, и «свободное» окно исчезло бы
из-под чужой записи. Прошлое не трогается вовсе.

**Скрытие — не удаление.** Скрытое окно остаётся в календаре мастера и
исчезает с публичной страницы: его не отдают ни `public-availability`, ни поиск
по длительности, ни `findPublicByIdForOrganization` — идентификаторы окон
публичны, и названное по памяти скрытое окно продаваться не должно. Обратный ход
стоит одно нажатие вместо повторной публикации, поэтому «уехала на неделю»
перестало означать «сотри и набери заново».

Занятое окно скрыть нельзя (`409`, код `slot_booked`): у клиента на руках
подтверждение с этим часом. `status = 'available'` стоит в самом `WHERE`, как у
переноса и удаления, — проигранная гонка возвращает `409` `slot_just_taken`, а
не молчаливое «сохранено». Периодом ответ приходит числом `changedCount`: уже
скрытые окна в счёт не идут, иначе отчёт не отличал бы работу от её отсутствия.
Прошлое не трогается.

**Окно внутри уже идущего визита не публикуется.** Окно длины не несёт, и до
этого правила «занято» читалось по статусам окон: визит на 195 минут, начатый в
18:30, держит одно окно 18:30, если больше в тот день не публиковали, — и час
19:00 вставал `available` поверх идущей работы. Теперь занятость считается
отрезками `[начало визита, начало + visitDurationMinutes)` по активным захватам
`booking_slots`:

- `POST /slots` на такой час отвечает `409` с кодом `slot_inside_booking` и
  полем `visitEndsAt` — экран говорит «В это время у вас идёт визит до 22:00»,
  а не «нельзя».
- `POST /slots/bulk` такие часы не создаёт и возвращает их отдельным числом
  `busyCount` — рядом со `skippedCount` («уже были опубликованы») и
  `inThePastCount`. Причины разные: пропущенное «уже было» мастер найдёт в
  календаре, а занятое визитом время в календаре отсутствует.

`?durationMinutes=N` — необязательный. Без него отдаются все открытые окна. С
ним — только те старты, куда визит такой длины действительно помещается: старт
не предлагается, если отрезок `[старт, старт + N)` пересекается с чужим визитом.
Пробелы в расписании по-прежнему ничего не блокируют — неопубликованное время не
является чужой записью.

Публичный ответ — проекция `{ id, startsAt, status }`, а не строка окна:
`organization_member_id` — внутренний адрес, публичная страница его никогда не
читала, и анониму он достаётся бесплатно. Обратная сторона того же: `id` окна
**является публичным значением**, поэтому любой маршрут, принимающий
`publishedSlotId`, обязан сам проверить принадлежность окна своей организации
(`findByIdForOrganization`) — знание идентификатора ничего не разрешает.

### 6.4. Bookings

| Метод | Путь                                            | Авторизация | Описание                                           |
| ----- | ----------------------------------------------- | ----------- | -------------------------------------------------- |
| GET   | `/organizations/{slug}/bookings`                | JWT + права | Записи мастера; сужается `?from`/`?to`/`?status`   |
| POST  | `/organizations/{slug}/bookings`                | JWT + права | Запись рукой мастера — можно на произвольное время |
| PATCH | `/organizations/{slug}/bookings/{id}`           | JWT + права | Смена статуса (подтвердить / завершить / отменить) |
| PATCH | `/organizations/{slug}/bookings/{id}/details`   | JWT + права | Правка: состав услуг, контакты гостя, заметка      |
| POST  | `/organizations/{slug}/public-bookings`         | не обяз.    | Запись со страницы мастера — гостем или вошедшим   |
| GET   | `/organizations/{slug}/public-bookings/{token}` | токен       | Статус своей записи для гостя                      |

**Списки сужаются строкой запроса, а не отдельными маршрутами.** У записей это
`?from`/`?to` (отрезок по времени **визита**, полуинтервал `[from, to)`) и
`?status` — одно значение из шести; у окон — те же `?from`/`?to`. Все три
необязательны, и без них ответ прежний: весь список.

Границы приходят полными метками времени, а не датами, и считает их кабинет:
сутки мастера принадлежат поясу её салона, и только у кабинета этот пояс есть.
Сервер не имеет своего мнения о том, когда начинается день, — ровно за
отсутствие этого правила сводка `/organizations/me/summary` считала «сегодня»
по часам UTC.

Сита независимы: счётчик непринятых записей в оболочке кабинета спрашивает
только `?status=pending` и никакого отрезка — запись, оставленная без ответа
неделю назад, это та же несделанная работа, что и вчерашняя.

Третье сито — `?clientId`: история визитов одного человека, то, что показывает
открытая карточка клиента. Оно заменяет список, а не дополняет его, и берёт
телефон из адресной книги, а не из адреса: номер — персональные данные, и
оседать ему в логах прокси и в истории браузера незачем. Клиент чужой
организации не находится — ответ `404`, а не чужие записи.

**Правка — отдельный маршрут от статуса.** `PATCH .../details` меняет состав
услуг, контакты гостя и заметку; `PATCH .../{id}` меняет статус. Разделены
потому, что это два разных решения с несвязанными причинами отказа: «дописать
услугу» может не пройти по занятости окон уже после того, как «подтвердить»
применилось.

Состав услуг заменяется целиком, а не дополняется: убрать услугу — такая же
обычная правка, как дописать. Он же тянет за собой время: длительность визита
меняется, поэтому окна перезахватываются в одной транзакции с правкой — свои
освобождаются, нужный отрезок берётся заново, всё или ничего. Не хватило
свободного времени подряд — `409 not_enough_time`, и запись остаётся ровно
такой, какой была.

Правятся только `pending` и `confirmed`. Завершённая — уже доход в отчётах,
отменённая отдала окна и они могли быть проданы; обе отвечают
`409 booking_not_editable`, а не `404`: запись есть, и мастер её видит.

Времени визита в этой правке нет — перенос живёт в расписании
(`PATCH .../slots/{id}`).

**Статусы одним PATCH, а не четырьмя путями.** `confirm`/`cancel`/`complete`/
`no-show` — это одно поле `status`, и отдельные маршруты под каждое значение
были бы четырьмя способами написать одно и то же.

**Но не любое значение поверх любого.** Отмена и завершение окончательны:
отменённая запись, вернувшаяся в `completed`, снова попадает в выручку
(`finance-summary` суммирует именно `completed`), хотя её окна уже освобождены и
могут принадлежать другому визиту. Исправить можно `no_show` — суждение,
принятое в моменте, при котором окна ещё удержаны. Полный список допустимых
переходов — `STATUSES_LEADING_TO` в `booking/domain/booking-status.ts`;
недопустимый переход отвечает `409`, а не `500`, и проверка встроена в сам
`UPDATE`, поэтому два одновременных запроса не могут оба её пройти.

**Клиент переносит визит сам — тем же правом, что и отменяет.** `POST
:slug/public-bookings/{token}/reschedule` для гостя и `POST
/client/visits/{id}/reschedule` для вошедшего; тело — `{ publishedSlotId }`.
Право спрашивается тем же `clientCancellationHours`: разные правила означали
бы, что человек, которому поздно отменять, всё ещё может уехать в другой день,
то есть отменить визит другими словами. Отказы приходят кодами отмены
(`cancellation_disabled`, `cancellation_too_late`).

Новое окно берётся у **того же** мастера, должно быть свободным, не скрытым и в
будущем; визит обязан помещаться в него целиком — те же правила, что при первой
записи. Освобождение старых окон, захват новых и переезд записи — одна
транзакция: неудачный перенос оставляет визит на прежнем месте, а не без
времени. Статус не меняется — подтверждение мастера значит «я приму этого
клиента», а что она свободна в новом часе, она уже сказала, опубликовав окно.
Мастер узнаёт push, напоминание переезжает вместе с визитом, письма клиенту нет:
он только что нажал кнопку и видит новое время на экране.

**Заявка без ответа гаснет сама.** Час визита прошёл, а мастер так и не
ответила — фоновый проход (раз в час, `BookingExpiryService`) переводит такую
запись в `expired`. Отдельное значение, а не «отменена мастером»: она ничего не
отменяла, и писать в историю клиента чужое решение нельзя. Руками этот статус не
ставится — `UpdateBookingStatusDto` его не принимает.

Срок — ровно время визита, ни минутой раньше: более короткий («сутки без
ответа») гасил бы настоящие записи у мастера, которая подтверждает раз в два дня,
и цена такой ошибки — потерянный клиент, а не грязный список. Окна при этом не
возвращаются в продажу: они в прошлом. Тупиком статус не является — из него
ведут `completed` и `no_show`: человек мог прийти и без подтверждения.

**Токен вместо аккаунта.** У гостя аккаунта нет, поэтому вернувшегося опознать
нечем. `bookings.public_token` — единственный ключ такого человека к собственной
записи; на нём держатся страница статуса и календарный файл. Неверный токен даёт
`404`, неотличимый от удалённой записи: эндпоинт не должен становиться способом
узнать, существует ли чужая запись.

**Вошедший клиент узнаётся сразу.** Маршрут остаётся открытым для всех, но
охраняется `OptionalJwtAuthGuard`: действующая кука делает запись сразу своей
(`bookings.client_user_id`), и визит виден в `/client/visits` без письма.
Три правила, каждое намеренно:

- `client_user_id` берётся **только из куки** — телу запроса это поле не
  принадлежит, иначе визиты приписывались бы чужим аккаунтам;
- привязка происходит только при `role = client`: визит мастера, открывшей
  чужую публичную страницу, остаётся гостевым;
- **просроченный или битый токен — это гость, а не `401`.** Кука живёт 12
  часов, и отказ на вчерашней сессии не пустил бы человека записаться вовсе —
  на маршруте, который и так открыт каждому.

Почта аккаунта в `guest_email` **не** переносится: связь держит
`client_user_id`, а адрес ушёл бы дальше в адресную книгу мастера
(`upsertClientFromBooking`) — человек его мастеру не давал.

Тело `POST .../public-bookings`:

```json
{
  "publishedSlotId": "uuid",
  "serviceIds": ["uuid-1", "uuid-2"],
  "guestName": "Anna",
  "guestPhone": "+371...",
  "guestInstagram": "anna.nails"
}
```

Ответ — **три поля, а не вся строка записи**: анонимному гостю незачем видеть
внутренние id, заметки мастера и `idempotencyKey`, тем более что в ответе теперь
есть секрет.

```json
{ "publicToken": "uuid", "status": "pending", "startsAt": "2026-08-15T09:00:00.000Z" }
```

`status` приходит `confirmed` сразу, если у мастера включено авто-подтверждение
(`organizations.auto_confirm_bookings`), иначе `pending`. Экран подтверждения на
странице различает эти два случая: обещать «ждём вас» там, где мастер ещё не
ответила, — неправда.

Ответ `GET .../public-bookings/{token}` — узкая проекция, собранная вручную, а
не через spread строки: заметки мастера и её пометки о клиенте не должны утечь
даже случайно.

```json
{
  "status": "pending",
  "startsAt": "2026-08-15T09:00:00.000Z",
  "durationMinutes": 60,
  "items": [
    {
      "name": "Маникюр",
      "durationMinutes": 60,
      "priceAmountMinorUnits": 3500,
      "priceCurrency": "EUR"
    }
  ]
}
```

`durationMinutes` — только рабочее время: буфер уборки принадлежит мастеру, а не
календарю клиента.

Бронирование выполняется атомарным условным `UPDATE ... WHERE status='available'`
сразу по всем окнам интервала (ARCHITECTURE.md §6), а не расчётом пересечений
диапазонов. Захват «всё или ничего»: частичный означал бы наложение на чужую
запись.

### 6.4a. Clients (адресная книга мастера)

| Метод        | Путь                                       | Авторизация | Описание                                              |
| ------------ | ------------------------------------------ | ----------- | ----------------------------------------------------- |
| GET/POST     | `/organizations/{slug}/clients`            | JWT + права | Список (со счётом визитов) и создание                 |
| PATCH/DELETE | `/organizations/{slug}/clients/{id}`       | JWT + права | Изменение / удаление                                  |
| PATCH        | `/organizations/{slug}/clients/{id}/block` | JWT + права | Блокировка: гость с этим телефоном не запишется       |
| POST         | `/organizations/{slug}/clients/{id}/merge` | JWT + права | Слияние дублей: в клиента из пути вливается `mergeId` |

**Дубли ловятся по правилу сравнения, а не уникальным индексом.** Индекс
`(organization_id, phone)` сравнивает строки, и «20000114» с «+37120000114»
проходили обе — в книге появлялся второй человек с той же историей визитов.
Создание и правка клиента теперь проверяют хвост номера (`phoneMatchKey`) и
отвечают тем же `409 client_phone_taken`.

Уже заведённые дубли склеиваются через `POST .../{id}/merge`. Историю визитов
переносить нечего: записи связаны с книгой номером, а не ключом, и обе карточки
давно указывают на одни и те же визиты. Переносится то, что мастер писала
руками, по правилу «ничего не теряем»: заметки складываются обе, пустые поля
заполняются из поглощаемой, блокировка ставится, если была хоть у одной.
Поглощённая карточка удаляется мягко — если слияние окажется ошибкой,
восстанавливать будет из чего.

**Счёт визитов приезжает со строкой списка.** У каждого клиента `visitStats`:
`totalBookings` (без отменённых) и `lastVisitAt` (последний **завершённый**
визит). Считает их база одним запросом на всю адресную книгу — соединение
с записями идёт по хвосту телефона, тем же правилом, что `phoneMatchKey`.
Раньше эти два числа считал кабинет, а для этого он скачивал **все** записи
организации.

Полная история одного клиента — это `GET /organizations/{slug}/bookings?clientId=…`
(§6.4), и запрашивается она только когда карточку открыли. Телефон в адрес не
попадает: номер — персональные данные, сервер достаёт его сам, попутно проверяя,
что клиент принадлежит этой организации.

Метка (`flag`) и заметка — приватные: они не входят ни в один публичный ответ.

### 6.4b. Finance

| Метод | Путь                                    | Авторизация | Описание                                      |
| ----- | --------------------------------------- | ----------- | --------------------------------------------- |
| GET   | `/organizations/{slug}/finance-summary` | JWT + права | Доход, средний чек, отмены, разрез по услугам |

Считается по ценам на момент записи для визитов со статусом `completed`. Это не
бухгалтерия: оплаты в продукте не проводятся, поэтому суммы отражают назначенную
стоимость, а не полученные деньги.

Сужается тем же `?from`/`?to`, что и списки, и отрезок применяется **ко всем**
числам разом. Это исправление: график по месяцам был ограничен последним годом,
а итоги считались за всё время, и экран показывал одно над другим, ничего об
этом не говоря.

`previousRevenue` — доход за столько же времени вплотную перед отрезком.
Правило одно и не требует второй пары границ: для «этого месяца» это прошлый
месяц, для «трёх месяцев» — три предыдущих. Без обеих границ сравнивать не с
чем, и поле равно `null`, а не нулю: у «всего времени» нет предыдущего всего
времени, а у отрезка без правого конца не определена длина.

### 6.7. Notifications

Реализовано ровно одно уведомление: **push мастеру о новой записи**. Клиенту
продукт по-прежнему не пишет ничего — он узнаёт решение мастера, вернувшись по
своей ссылке (§6.4), а напоминание получает от собственного календаря, через
будильник внутри `.ics`. Остальной Epic 6 в TASKS.md открыт: очереди с
повторами нет, SMS нет, писем о записях нет.

Web Push по RFC 8291/8292: подписку выдаёт браузер устройства, сервер шифрует
тело её ключами и подписывается перед push-сервисом парой VAPID. Все три
эндпоинта требуют токен и работают в границах вошедшего пользователя —
подписка принадлежит человеку и его устройству, а не организации.

| Метод  | Путь                                | Описание                                                  |
| ------ | ----------------------------------- | --------------------------------------------------------- |
| GET    | `/notifications/push/key`           | Открытый ключ VAPID; `{"publicKey": null}` — не настроено |
| POST   | `/notifications/push/subscriptions` | Сохранить подписку устройства (upsert по `endpoint`)      |
| DELETE | `/notifications/push/subscriptions` | Забыть подписку; `endpoint` в теле, не в строке запроса   |

`POST` принимает `{ endpoint, p256dh, auth, userAgent? }` — то, что браузер
отдаёт в `PushSubscription.toJSON()`. Повторная отправка той же подписки не
ошибка, а норма: кабинет присылает её при каждом открытии, и так чинится
рассинхронизация, если строку на сервере уже убрали как мёртвую.

Мёртвые подписки сервер удаляет сам, по ответу push-сервиса `404`/`410` в
момент отправки. Отдельного эндпоинта для этого нет и не нужно.

Ограничение платформы, которое обязан знать фронтенд: на iOS Web Push
существует только для приложения, добавленного на экран «Домой» — во вкладке
Safari `PushManager` не объявлен. Кабинет различает этот случай отдельно
(`needs-install`) и объясняет, что делать.

| Метод     | Путь                           | Описание    |
| --------- | ------------------------------ | ----------- |
| GET       | `/me/notifications`            | Планируется |
| PATCH     | `/me/notifications/{id}/read`  | Планируется |
| GET/PATCH | `/me/notification-preferences` | Планируется |

### 6.7a. Client Account (кабинет клиента)

| Метод | Путь                      | Авторизация | Описание                                           |
| ----- | ------------------------- | ----------- | -------------------------------------------------- |
| POST  | `/client/sign-in/request` | —           | Просит ссылку для входа; всегда `204`              |
| POST  | `/client/sign-in/confirm` | —           | Гасит ссылку, открывает сессию, привязывает визиты |
| POST  | `/client/visits/claim`    | JWT         | Забрать запись себе по её токену — без письма      |
| GET   | `/client/profile`         | JWT         | Имя и телефон для подстановки в форму записи       |
| GET   | `/client/visits`          | JWT         | Визиты клиента ко **всем** мастерам                |

**Почему не под `/organizations/{slug}`.** У визитов к разным мастерам нет общей
организации: клиент, который ходит и к Анне, и к Марису, видит один список. Адрес,
принадлежащий одной из них, врал бы о том, чей это список.

**Пароля у клиента нет.** Он заходит несколько раз в год; пароль, заведённый ради
такого, будет либо забыт, либо повторён с чужого сайта. Ссылка из письма живёт час
и срабатывает один раз (`user_tokens.purpose = 'client_sign_in'`, DATABASE.md
§3.14b).

Запрос принимает `email`, либо `publicToken` записи (кнопка «запомнить меня» на
странице статуса), либо оба. Ответ **всегда** `204` и никогда не сообщает, нашёлся
ли адрес: иначе форма становится проверялкой «а этот человек здесь записывался».
Единственное исключение — `400 client_email_required`: вход начат со страницы
записи, в которой адреса нет (при записи он необязателен), и экрану нужно его
спросить. Это ответ про ту самую запись, чью секретную ссылку спрашивающий уже
держит, — о постороннем он не рассказывает.

**Мастеру и администратору ссылка не уходит вовсе.** Письмо «войдите одним
нажатием» открывало бы полный доступ к чужому бизнесу тому, кто добрался до
почтового ящика, не спрашивая даже старого пароля. Ответ при этом неотличим от
ответа на незнакомый адрес.

**Вошедшему письмо самому себе не нужно.** `POST /client/visits/claim` с
`publicToken` привязывает одну запись сразу: доказательств у человека уже два —
действующая сессия и секретная ссылка, которая и так открывает статус записи и
её отмену. Замок тот же (`client_user_id IS NULL`), поэтому чужую запись не
перехватить. Чужая запись и несуществующая ссылка отвечают одинаковым `404`:
иначе по ответу можно было бы отличить одно от другого.

**`GET /client/profile` — только для `role = client`,** иначе `403`. Имя и
телефон берутся из последнего визита, а не из `users`: телефон там глобально
уникален, и хранить в нём введённое в форме значит однажды упасть на двух
аккаунтах с одним номером. Почты в ответе нет — форма записи её не спрашивает,
и платформа её у клиента не собирает.

**Склейка записей — только по доказанному адресу.** В момент подтверждения к
аккаунту привязываются: запись, со страницы которой начат вход (её пустой
`guest_email` при этом заполняется), и все прочие записи с тем же адресом.
Совпадение телефона доказательством не считается — его вписывают с ошибкой и
вписывают чужой, а склеенные по нему записи показали бы одному человеку визиты
другого. Уже привязанную к другому аккаунту запись перехватить нельзя
(`client_user_id IS NULL` в условии).

**«Повторить визит».** Каждый визит несёт `serviceIds` — идентификаторы услуг в
**сегодняшнем** каталоге мастера, а не снимки из `booking_items`. Кабинет строит
из них адрес `{slug}?services=id,id`, и страница мастера открывает запись с уже
собранной корзиной. Услугу, которой в каталоге больше нет, страница молча не
берёт: показывать цену, которую никто не назначал, нельзя.

**Секретный токен своей записи** (`publicToken`) и **адрес салона** одной строкой
входят в ответ ради одного: подтверждённый визит обязан попадать в календарь и из
кабинета, а не только с экрана сразу после записи. Календарный файл собирает
маршрут веба по паре «мастер + токен», потому что его адрес должен открываться и
без сессии; место события без адреса отправляло бы человека вспоминать, куда он
идёт. Владельцу визита этот токен и так принадлежит — он открывает ровно то, что
человек и без него может: статус своей записи и её отмену.

**Что клиент видит и чего не видит.** Ответ `/client/visits` собран по полю:
время, длительность работы, услуги со снимком цены, slug, публичное имя, адрес
и телефон мастера. Телефон — не украшение карточки: самостоятельная отмена
выключена по умолчанию, и без номера кабинет не мог предложить визиту ничего,
хотя страница записи по той же записи предлагает позвонить.
Заметки мастера, её метка на клиенте и внутренние идентификаторы не входят в него
никогда — карточка клиента в CRM остаётся приватной, как и сказано в §6.4a. В
обратную сторону так же: мастер нигде не узнаёт, что её клиент ходит ещё к кому-то.

### 6.7b. Отмена визита клиентом

| Метод | Путь                                                   | Авторизация  | Описание                          |
| ----- | ------------------------------------------------------ | ------------ | --------------------------------- |
| POST  | `/organizations/{slug}/public-bookings/{token}/cancel` | токен записи | Отмена гостем со страницы статуса |
| POST  | `/client/visits/{id}/cancel`                           | JWT          | Отмена вошедшим клиентом          |

**Правило принадлежит мастеру.** `organizations.client_cancellation_hours`: `null`
— клиент отменить не может вовсе (умолчание, сегодняшнее поведение), число N —
может, пока до визита остаётся не меньше N часов. Часы, а не «можно/нельзя»,
потому что мастеру важно не то, отменит ли клиент, а успеет ли она продать
освободившееся время.

Оба входа обслуживает одна услуга (`CancelByClientService`): разъедини их — и
вошедший клиент однажды отменит там, где гость уже не может, потому что правило
поправят в одном месте из двух.

Отказы несут `code` (`packages/shared-kernel/src/booking-error.ts`), потому что
объяснять их приходится человеку, языка которого сервер не знает:

| Код                         | Статус | Когда                                            |
| --------------------------- | ------ | ------------------------------------------------ |
| `cancellation_disabled`     | 403    | Мастер не включала самостоятельную отмену        |
| `cancellation_too_late`     | 409    | До визита осталось меньше разрешённого срока     |
| `cancellation_not_possible` | 409    | Визит уже отменён, состоялся или отмечен неявкой |

Чужая запись у вошедшего клиента отвечает `404`, а не `403`: перебором
идентификаторов иначе можно узнать, что чей-то визит существует.

**Что видит экран.** Ответы `GET /organizations/{slug}/public-bookings/{token}` и
`GET /client/visits` несут `cancellableUntil` — момент, а не правило: странице
нужен один ответ «рисовать ли кнопку», а «за сколько часов» — внутренняя
настройка мастера, которую посетителю знать незачем. `null` — кнопки нет.

После отмены освобождаются **все** окна визита, а не только начальное, и мастеру
уходит push: освободившийся час продаётся, только пока он не прошёл.

### 6.8. Admin (platform_admin)

| Метод | Путь                                         | Описание                                                |
| ----- | -------------------------------------------- | ------------------------------------------------------- |
| GET   | `/admin/organizations`                       | Салоны: владелец, счётчики, тариф, поиск, страницы      |
| GET   | `/admin/summary`                             | Метрики платформы: мастера, клиенты, записи, подписки   |
| GET   | `/admin/trends`                              | Регистрации и записи по неделям за 12 недель            |
| GET   | `/admin/masters`                             | Мастера с поиском и фильтром по статусу                 |
| PATCH | `/admin/masters/{userId}/status`             | Блокировка / разблокировка мастера                      |
| GET   | `/admin/users`                               | Пользователи с фильтром по роли                         |
| PATCH | `/admin/users/{userId}/status`               | Блокировка / разблокировка                              |
| PATCH | `/admin/users/{userId}/role`                 | Смена системной роли                                    |
| GET   | `/admin/logs`                                | Журнал административных действий                        |
| GET   | `/admin/registration-requests`               | Очередь заявок: поиск, фильтр по состоянию, страницы    |
| GET   | `/admin/registration-requests/pending-count` | Сколько заявок ждут ответа (значок в меню)              |
| POST  | `/admin/registration-requests/{id}/approve`  | Одобрить: заводит аккаунт или зовёт подтвердить переход |
| POST  | `/admin/registration-requests/{id}/reject`   | Отклонить с причиной (уходит письмом)                   |
| PATCH | `/admin/organizations/{id}/status`           | `active` / `suspended` / `archived`                     |
| GET   | `/admin/masters/{userId}`                    | Карточка мастера: салоны, счётчики, журнал действий     |
| GET   | `/admin/subscription-plans`                  | Тарифы                                                  |
| GET   | `/admin/subscriptions`                       | Подписки организаций                                    |
| POST  | `/admin/subscriptions`                       | Назначить / сменить тариф                               |
| PATCH | `/admin/subscriptions/{id}/status`           | Заморозить / разморозить / отменить                     |
| GET   | `/admin/platform-settings`                   | Настройки платформы                                     |
| PATCH | `/admin/platform-settings`                   | Изменение настроек                                      |

**Собственный аккаунт администратору отсюда не подчиняется.** `PATCH`
`/admin/users/{userId}/status`, `/admin/users/{userId}/role` и
`/admin/masters/{userId}/status` отвечают `403` с кодом `cannot_target_self`,
если `userId` — это сам вошедший. До этой проверки оба запроса на себя отвечали
`200`, и единственный администратор платформы становился клиентом: заявки
некому одобрять, роль некому вернуть, восстановление — прямой `UPDATE` в базе.

**Последнего администратора нельзя разжаловать и чужими руками.** Смена роли
`platform_admin` → любая другая отвечает `409` с кодом `last_admin`, если этот
администратор остался один. Пересчёт идёт в одной транзакции с `UPDATE` и
блокирует строки администраторов (`FOR UPDATE`): без блокировки двое
администраторов, разжалующие друг друга одновременно, оба увидят «нас двое» и
оба пройдут.

`/admin/logs` пишет действия администратора: блокировки, смены роли,
решения по заявкам, приостановку салонов, вход в кабинет мастера,
объявления и тарифы. Это не аудит всего продукта — действия самих мастеров
в него не попадают.

Для мастера объявления доступны отдельной парой маршрутов:

| Метод | Путь                          | Описание                                        |
| ----- | ----------------------------- | ----------------------------------------------- |
| GET   | `/announcements/active`       | Что показать сейчас, кроме уже прочитанного     |
| POST  | `/announcements/{id}/dismiss` | Отметка «прочитано» (на сервере, не в браузере) |

У одобрения два исхода, и они размечены полем `mode`:

```json
{ "mode": "created", "userId": "…", "organizationSlug": "alisa-ozola" }
```

```json
{ "mode": "confirmation-sent", "email": "alisa@example.com" }
```

Второй — когда на адрес заявки уже заведён аккаунт клиента. Второго аккаунта на
ту же почту не бывает, а человек тот же, и его записи должны остаться при нём:
кабинет мастера откроется на том же аккаунте, когда он подтвердит переход по
ссылке из письма (`POST /auth/registration/confirm-upgrade`, §2). До этого заявка
числится одобренной, но `created_user_id` у неё пуст — панель показывает такую
как «Ждёт подтверждения».

Отказы одобрения приходят `409` с машинным кодом рядом с фразой
(`registration_email_is_master`, `registration_account_blocked`,
`registration_phone_taken`, `registration_email_taken`) — панель говорит на трёх
языках, а `message` написан по-русски. Заявка при таком отказе возвращается в
очередь: «одобрена, но ничего не произошло» — это заявка, потерянная из работы.

Пример `POST /admin/registration-requests/{id}/reject`:

```json
{ "reason": "Платформа пока открыта только для мастеров в Латвии." }
```

Причина обязательна и не короче 10 символов: она уходит человеку письмом и остаётся единственным, что он о решении узнает.

Списки админки (`masters`, `users`, `organizations`, `registration-requests`) принимают `?query=&status=&role=&limit=&offset=` и отвечают `{ items, total }`.

## 8. Rate Limiting

Базовый лимит применён глобально (`ThrottlerModule` + `APP_GUARD`), а не по
контроллерам: ограничитель, который надо не забыть повесить на новый маршрут, —
это ограничитель, которого на новом маршруте не будет. Ответ при превышении —
`429`.

| Маршрут                                   | Лимит       | Почему именно столько                                                     |
| ----------------------------------------- | ----------- | ------------------------------------------------------------------------- |
| всё остальное                             | 120 / мин   | Экран кабинета честно веером даёт десяток запросов; это порог для скрипта |
| `POST /auth/login`                        | 10 / мин    | Человек не входит десять раз в минуту, перебор требует тысяч попыток      |
| `POST /auth/register`                     | 5 / час     | Инвайт-код — 31⁸ комбинаций, и пять попыток в час его таким и оставляют   |
| `PATCH /auth/me/password`                 | 5 / 5 мин   | Проверка текущего пароля не должна работать оракулом                      |
| `POST .../public-bookings`                | 10 / час    | Единственный неаутентифицированный **пишущий** маршрут: каждый запрос     |
|                                           |             | забирает реальное окно из календаря мастера                               |
| `POST /client/sign-in/request`            | 5 / час     | Шлёт письмо на чужой адрес: без лимита кнопка «запомнить меня» —          |
|                                           |             | рассылка по чужому ящику                                                  |
| `POST /client/sign-in/confirm`            | 10 / 10 мин | Токен 256 бит, но перебирать его не должно быть дёшево                    |
| `POST /client/visits/claim`               | 10 / 10 мин | Аргумент — секретный токен записи: тот же перебор, тот же лимит           |
| `POST .../public-bookings/{token}/cancel` | 10 / час    | Второй и последний неаутентифицированный **пишущий** маршрут              |

**Кого считаем — не то же, что «откуда пришёл запрос».** Браузеры не обращаются
к API напрямую: они ходят в Next-BFF (`/api/proxy`), который вызывает API
server-to-server. По умолчанию адрес сокета у всех запросов один и тот же, и
лимит «5 гостевых записей в час» означал бы пять на весь продукт, а один шумный
посетитель закрывал бы вход всем. Поэтому `ClientThrottlerGuard` берёт, по
порядку: субъект токена (авторизованный трафик считается по аккаунту — это и
честнее, и осмысленнее адреса, когда мастера сидят за одним NAT); затем
исходный адрес из `X-Forwarded-For`, который BFF передаёт во всех трёх местах,
где обращается к API; затем адрес сокета.

Левое значение `X-Forwarded-For` подставляется клиентом, то есть подделываемо
всем, что может достучаться до API напрямую. В текущей топологии такого пути нет
— BFF единственный вход (см. DEPLOYMENT.md), — и IP используется только для
вызывающих, у которых ещё нет личности. Если API однажды опубликуют напрямую,
этот хоп должен стать подписанным, а не заголовком на честном слове.

Счётчики живут в памяти процесса: при горизонтальном масштабировании лимит
станет «N на инстанс». Перенос на Redis (уже в `REDIS_URL`) идёт вместе с `A-5`.

## 9. Альтернативы и открытые вопросы

1. **REST vs GraphQL:** REST выбран для MVP как более простой в кэшировании (важно для публичных страниц) и предсказуемый в контрактах. GraphQL может быть пересмотрен для Admin/Analytics модуля при росте сложности запросов (Phase 3+) — требует отдельного решения.
2. **OpenAPI-спецификация:** должна поддерживаться в актуальном состоянии параллельно с реализацией (генерация клиентских типов из схемы) — формат/инструмент фиксируется на этапе реализации.
3. **Realtime-обновления** (напр. live-обновление доступности слотов в UI мастера) — кандидат на WebSocket/SSE, вне MVP.
