# API — AMOLIE

Версия 0.3 (черновик для утверждения). Стиль API: **REST** (предложение — см. §9 об альтернативах).

## 1. Общие принципы

- Базовый путь: `/api/v1`. Версионирование через префикс пути.
- Формат данных: JSON (`Content-Type: application/json`), UTF-8.
- Все временные метки — ISO 8601 в UTC (`2026-07-30T14:00:00Z`), конвертация в локальный часовой пояс — на клиенте.
- Деньги в ответах API передаются как объект `{ amount: number (в центах), currency: string }`, никогда как float в валюте.
- Идентификаторы — UUID-строки.
- Аутентификация: `Authorization: Bearer <access_token>`.
- Мультиарендность: контекст организации определяется из токена/пути, клиент не может передать произвольный `organization_id` для чтения чужих данных.

## 2. Аутентификация и авторизация

### 2.1. Формат токенов

- `access_token` — JWT, TTL 15 минут, передаётся в заголовке.
- `refresh_token` — httpOnly secure cookie, TTL 30 дней, используется только эндпоинтом обновления токена.

### 2.2. Эндпоинты

| Метод | Путь                    | Описание                                                                                                                             |
| ----- | ----------------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| POST  | `/auth/register`        | Регистрация мастера/организации. **Требует `inviteCode`** (закрытая регистрация в MVP, см. [ARCHITECTURE.md](ARCHITECTURE.md) §10.1) |
| POST  | `/auth/login`           | Вход по паролю. Ответ включает `redirectUrl` (см. ниже)                                                                              |
| POST  | `/auth/otp/request`     | Запрос одноразового кода на телефон/email                                                                                            |
| POST  | `/auth/otp/verify`      | Подтверждение OTP → выдача токенов                                                                                                   |
| POST  | `/auth/refresh`         | Обновление access-токена по refresh-токену                                                                                           |
| POST  | `/auth/logout`          | Инвалидация refresh-токена                                                                                                           |
| POST  | `/auth/password/forgot` | Запрос сброса пароля                                                                                                                 |
| POST  | `/auth/password/reset`  | Установка нового пароля по токену сброса                                                                                             |

Пример `POST /auth/register` (регистрация мастера/организации, MVP — закрытая):

```json
{
  "inviteCode": "A7QK3M2P",
  "fullName": "Anna Bērziņa",
  "email": "anna@example.com",
  "password": "...",
  "organizationName": "Anna Nails Studio",
  "desiredSlug": "anna-nails"
}
```

Невалидный/использованный/истёкший код → `409` в формате из §3. При успехе — ответ как у `/auth/login` (см. ниже), пользователь уже авторизован в только что созданной организации.

Пример ответа `POST /auth/login`:

```json
{
  "accessToken": "...",
  "user": { "id": "uuid", "fullName": "Anna Bērziņa", "role": "master" },
  "redirectUrl": "https://anna-nails.amolie.com/dashboard"
}
```

`redirectUrl` вычисляется backend'ом по правилам из [ARCHITECTURE.md](ARCHITECTURE.md) §3.6: есть организация → её поддомен; нет — остаётся `null` (пользователь остаётся на `amolie.com`).

### 2.3. Роли и доступ

Проверка прав — на уровне Application-слоя backend (см. [ARCHITECTURE.md](ARCHITECTURE.md) §15). Общая матрица:

| Роль             | Доступ                                                                                            |
| ---------------- | ------------------------------------------------------------------------------------------------- |
| `client`         | Свои записи, свой профиль, публичные данные организаций                                           |
| `master`         | Данные своей организации: расписание, записи, услуги (в рамках прав, назначенных `admin`/`owner`) |
| `admin`/`owner`  | Полное управление организацией, сотрудниками, биллингом                                           |
| `platform_admin` | Административные эндпоинты `/admin/*`, доступ ко всем организациям                                |

## 3. Формат ошибок

Единый формат на основе RFC 7807 (Problem Details):

```json
{
  "type": "https://amolie.com/errors/booking-slot-unavailable",
  "title": "Slot is no longer available",
  "status": 409,
  "detail": "Выбранный слот был занят другим клиентом.",
  "instance": "/api/v1/bookings",
  "traceId": "a1b2c3d4"
}
```

Коды состояния:

- `400` — некорректный запрос (валидация).
- `401` — не аутентифицирован.
- `403` — нет прав.
- `404` — сущность не найдена.
- `409` — конфликт (напр. слот занят, дублирующийся email).
- `422` — семантически некорректные данные.
- `429` — превышен rate limit.
- `500` — внутренняя ошибка.

## 4. Пагинация, фильтрация, сортировка

- Пагинация — курсорная для лент (записи, уведомления): `?cursor=<opaque>&limit=20`.
- Ответ со списком:

```json
{
  "data": [/* ... */],
  "meta": { "nextCursor": "opaque-string-or-null" }
}
```

- Фильтрация — явные query-параметры (`?status=confirmed&from=2026-08-01&to=2026-08-07`), без свободного query-языка в MVP.
- Сортировка — `?sort=starts_at:asc`.

## 5. Идемпотентность

Все небезопасные операции создания критичных сущностей (`POST /bookings`, `POST /payments`) принимают заголовок `Idempotency-Key`. Повторный запрос с тем же ключом в течение 24 часов возвращает результат первого выполнения без повторного создания сущности.

## 6. Ключевые группы эндпоинтов

**Этот раздел описывает то, что действительно есть в коде.** Пути, отличающиеся
от первоначального плана, отличаются осознанно: master-facing CRUD живёт под
`/organizations/{slug}/...` (не `/organizations/me/...` — `OrgMembershipGuard`
резолвит организацию из `:slug`), а публичные эндпоинты помечены префиксом
`public-`, потому что путь без префикса уже занят guarded-контроллером той же
сущности, и два контроллера не могут владеть одним путём.

Разделы 6.5–6.7 — планируемое; они помечены явно.

### 6.1. Organizations & Profile

| Метод | Путь                            | Авторизация | Описание                                                       |
| ----- | ------------------------------- | ----------- | -------------------------------------------------------------- |
| GET   | `/organizations/me`             | JWT         | Организация текущего пользователя                              |
| GET   | `/organizations/me/summary`     | JWT         | Сводка для главной кабинета: ближайшие, клиенты, доход, лента  |
| PATCH | `/organizations/{slug}/profile` | JWT + права | Профиль и оформление публичной страницы (частичное обновление) |
| GET   | `/organizations/{slug}`         | —           | Публичный профиль для страницы записи                          |

`PATCH .../profile` принимает любое подмножество полей. Экраны кабинета
пользуются этим: переключатель авто-подтверждения в разделе «Записи» шлёт одно
поле, а не всю форму страницы — PATCH, несущий неотредактированные описание и
контакты, способен затереть их по случайности.

`designPresetKey` — единственное поле профиля с проверкой права, а не только
формата: мир вне предложения каталога принимается лишь у той организации,
которой он выдан (`custom_design_key`), иначе `403`
([DESIGN_STUDIO.md](DESIGN_STUDIO.md) §7.4a).

Локации и сотрудники (`/members`, `/locations`) в MVP не реализованы: продукт
рассчитан на одиночного мастера (PRD.md §2).

#### Публичный адрес страницы

| Метод | Путь                                                       | Авторизация                 | Описание                             |
| ----- | ---------------------------------------------------------- | --------------------------- | ------------------------------------ |
| GET   | `/organizations/{slug}/public-address/availability?value=` | JWT + `org:settings:manage` | Свободен ли адрес; отвечает причиной |
| PATCH | `/organizations/{slug}/public-address`                     | JWT + `org:settings:manage` | Сменить адрес страницы               |

Адрес намеренно вынесен из `PATCH .../profile`: это не поле профиля, а
идентификатор, который держат в руках другие люди. Смена переносит каждую
ссылку, что мастер раздала, поэтому у операции свои правила — валидация против
`shared-kernel` (`validatePublicSlug`: длина, формат, список зарезервированных
платформой слов), проверка занятости, лимит 3 смены за 30 дней и запись
прежнего адреса в историю. Право `org:settings:manage` (владелец), а не
`org:profile-page:manage`: администратор салона, которому можно переписать
страницу, не должен иметь возможности её **перенести**.

`GET .../availability` отвечает 200 всегда, даже когда адрес не годится:
поле спрашивает на каждом нажатии клавиши, и интерфейс, которому нужно поймать
исключение, чтобы показать подсказку, краснеет раньше, чем мастер дописала
второй символ. Форма ответа: `{ slug, available, reason, current }`, где
`reason` — код (`too-short` | `too-long` | `format` | `reserved` | `taken`),
а слова подбирает панель на языке мастера. `PATCH` при отказе отвечает 409 с
тем же кодом в поле `reason` (плюс `too-many-changes`).

Прежний адрес продолжает работать: `GET /organizations/{slug}` для него
отвечает 404 с полем `movedTo` — текущим адресом организации, — а публичная
страница превращает это в 308 (см. `organization_slug_history` в
[DATABASE.md](DATABASE.md) §3.2a).

#### Онбординг — пошаговая настройка кабинета

| Метод | Путь                   | Авторизация | Описание                                       |
| ----- | ---------------------- | ----------- | ---------------------------------------------- |
| GET   | `/onboarding`          | JWT         | Состояние настройки: шаги, прогресс, следующий |
| POST  | `/onboarding/complete` | JWT         | «Готово» — идемпотентно                        |
| POST  | `/onboarding/restart`  | JWT         | Пройти настройку заново                        |

Верхнеуровневый путь, а не `/organizations/...`: контроллер организаций владеет
`:slug`, и каждый добавленный туда маршрут приходится защищать от прочтения как
имени мастера. Организация резолвится из членства — вызывающий её не называет.

Ответ: `{ slug, completedAt, steps: [{ key, done, optional }], nextStep }`.
Шаги — `address`, `profile`, `design`, `services`, `schedule`, `share` —
именно в этом порядке: каждый предыдущий является условием следующего.
**Готовность шага выводится из данных, а не хранится**: сохранённая галочка
«шаг 4 пройден» — утверждение о прошлом, а `serviceCount > 0` — факт о
настоящем, и они расходятся в тот момент, когда мастер удаляет услугу,
созданную при настройке. В базе живёт только `onboarding_completed_at`: «я
закончила с этим экраном» — действительно решение, а не факт о данных.
`share` (первая запись) помечен `optional`: его закрывает клиент, и чек-лист,
который не даёт себя закрыть, пока не сделал кто-то другой, не закрывается
никогда.

#### Design Studio — облик публичной страницы

Контракт режима Студии ([DESIGN_STUDIO.md](DESIGN_STUDIO.md) §7). Все пути
охраняются JWT, членством в организации и правом `org:profile-page:manage`.

| Метод  | Путь                                         | Описание                                                      |
| ------ | -------------------------------------------- | ------------------------------------------------------------- |
| GET    | `/organizations/{slug}/page-design`          | Опубликованное, черновик, признак архива и история публикаций |
| PUT    | `/organizations/{slug}/page-design/draft`    | Автосохранение черновика; на публику не попадает              |
| DELETE | `/organizations/{slug}/page-design/draft`    | «Вернуться к опубликованному» — сброс черновика               |
| POST   | `/organizations/{slug}/page-design/publish`  | Публикация; пустое тело публикует текущий черновик            |
| POST   | `/organizations/{slug}/page-design/rollback` | Откат: новая публикация слепка версии `{version}`             |

Тело — решения мастера по десяти ручкам (`PageDesign` в `shared-kernel`), а не
значения токенов. **Сервер не доверяет клиенту** (§7.4): ключи вне списка
ручек отбрасываются, значения вне каталогов заменяются авторскими, цвета
доводятся автокоррекцией до проходящей норму ступени, производные
(`--accent-contrast`, `--accent-soft`) не принимаются никогда и всегда
выводятся резолвером. Поэтому запрос не отклоняется за «неправильный» цвет —
он сохраняет исправленный: непроходящего в базе не существует.

Прежние поля оформления (`designPresetKey`, `themeOverrides`, `heroStyle`,
`coverUrl`…) остаются в `PATCH .../profile` и синхронизируются публикацией:
пока их читает хоть один потребитель, два представления обязаны быть в
согласии.

### 6.3. Availability (мастер публикует окна вручную)

**Продуктовое решение MVP (PRD.md §7.4):** без рабочих часов и расписания.
`published_slots` — конечный список конкретных окон, опубликованных вручную;
ничего не вычисляется.

| Метод        | Путь                                        | Авторизация | Описание                                        |
| ------------ | ------------------------------------------- | ----------- | ----------------------------------------------- |
| GET/POST     | `/organizations/{slug}/slots`               | JWT + права | Свои окна (включая занятые) и публикация одного |
| POST         | `/organizations/{slug}/slots/bulk`          | JWT + права | Публикация периода: даты × дни недели × шаг     |
| PATCH/DELETE | `/organizations/{slug}/slots/{id}`          | JWT + права | Перенос / удаление свободного окна              |
| GET          | `/organizations/{slug}/public-availability` | —           | Только `available`; см. `durationMinutes` ниже  |

`?durationMinutes=N` — необязательный. Без него отдаются все открытые окна. С
ним — только те старты, куда визит такой длины действительно помещается: окно
не предлагается, если внутри интервала уже есть занятое время. Пробелы в
расписании ничего не блокируют — неопубликованное время не является чужой
записью.

Публичный ответ — проекция `{ id, startsAt, status }`, а не строка окна:
`organization_member_id` — внутренний адрес, публичная страница его никогда не
читала, и анониму он достаётся бесплатно. Обратная сторона того же: `id` окна
**является публичным значением**, поэтому любой маршрут, принимающий
`publishedSlotId`, обязан сам проверить принадлежность окна своей организации
(`findByIdForOrganization`) — знание идентификатора ничего не разрешает.

### 6.4. Bookings

| Метод | Путь                                            | Авторизация | Описание                                           |
| ----- | ----------------------------------------------- | ----------- | -------------------------------------------------- |
| GET   | `/organizations/{slug}/bookings`                | JWT + права | Все записи мастера                                 |
| POST  | `/organizations/{slug}/bookings`                | JWT + права | Запись рукой мастера — можно на произвольное время |
| PATCH | `/organizations/{slug}/bookings/{id}`           | JWT + права | Смена статуса (подтвердить / завершить / отменить) |
| POST  | `/organizations/{slug}/public-bookings`         | —           | Гостевая запись со страницы мастера                |
| GET   | `/organizations/{slug}/public-bookings/{token}` | токен       | Статус своей записи для гостя                      |

**Статусы одним PATCH, а не четырьмя путями.** `confirm`/`cancel`/`complete`/
`no-show` — это одно поле `status`, и отдельные маршруты под каждое значение
были бы четырьмя способами написать одно и то же.

**Но не любое значение поверх любого.** Отмена и завершение окончательны:
отменённая запись, вернувшаяся в `completed`, снова попадает в выручку
(`finance-summary` суммирует именно `completed`), хотя её окна уже освобождены и
могут принадлежать другому визиту. Исправить можно `no_show` — суждение,
принятое в моменте, при котором окна ещё удержаны. Полный список допустимых
переходов — `STATUSES_LEADING_TO` в `booking/domain/booking-status.ts`;
недопустимый переход отвечает `409`, а не `500`, и проверка встроена в сам
`UPDATE`, поэтому два одновременных запроса не могут оба её пройти.

**Токен вместо аккаунта.** Аккаунтов у клиентов нет, поэтому вернувшегося гостя
нечем опознать. `bookings.public_token` — единственный ключ человека к
собственной записи; на нём держатся страница статуса и календарный файл.
Неверный токен даёт `404`, неотличимый от удалённой записи: эндпоинт не должен
становиться способом узнать, существует ли чужая запись.

Тело `POST .../public-bookings`:

```json
{
  "publishedSlotId": "uuid",
  "serviceIds": ["uuid-1", "uuid-2"],
  "guestName": "Anna",
  "guestPhone": "+371...",
  "guestInstagram": "anna.nails"
}
```

Ответ — **три поля, а не вся строка записи**: анонимному гостю незачем видеть
внутренние id, заметки мастера и `idempotencyKey`, тем более что в ответе теперь
есть секрет.

```json
{ "publicToken": "uuid", "status": "pending", "startsAt": "2026-08-15T09:00:00.000Z" }
```

`status` приходит `confirmed` сразу, если у мастера включено авто-подтверждение
(`organizations.auto_confirm_bookings`), иначе `pending`. Экран подтверждения на
странице различает эти два случая: обещать «ждём вас» там, где мастер ещё не
ответила, — неправда.

Ответ `GET .../public-bookings/{token}` — узкая проекция, собранная вручную, а
не через spread строки: заметки мастера и её пометки о клиенте не должны утечь
даже случайно.

```json
{
  "status": "pending",
  "startsAt": "2026-08-15T09:00:00.000Z",
  "durationMinutes": 60,
  "items": [
    {
      "name": "Маникюр",
      "durationMinutes": 60,
      "priceAmountMinorUnits": 3500,
      "priceCurrency": "EUR"
    }
  ]
}
```

`durationMinutes` — только рабочее время: буфер уборки принадлежит мастеру, а не
календарю клиента.

Бронирование выполняется атомарным условным `UPDATE ... WHERE status='available'`
сразу по всем окнам интервала (ARCHITECTURE.md §6), а не расчётом пересечений
диапазонов. Захват «всё или ничего»: частичный означал бы наложение на чужую
запись.

### 6.4a. Clients (адресная книга мастера)

| Метод        | Путь                                       | Авторизация | Описание                                        |
| ------------ | ------------------------------------------ | ----------- | ----------------------------------------------- |

## 8. Rate Limiting

Базовый лимит применён глобально (`ThrottlerModule` + `APP_GUARD`), а не по
контроллерам: ограничитель, который надо не забыть повесить на новый маршрут, —
это ограничитель, которого на новом маршруте не будет. Ответ при превышении —
`429`.

| Маршрут                    | Лимит     | Почему именно столько                                                     |
| -------------------------- | --------- | ------------------------------------------------------------------------- |
| всё остальное              | 120 / мин | Экран кабинета честно веером даёт десяток запросов; это порог для скрипта |
| `POST /auth/login`         | 10 / мин  | Человек не входит десять раз в минуту, перебор требует тысяч попыток      |
| `POST /auth/register`      | 5 / час   | Инвайт-код — 31⁸ комбинаций, и пять попыток в час его таким и оставляют   |
| `PATCH /auth/me/password`  | 5 / 5 мин | Проверка текущего пароля не должна работать оракулом                      |
| `POST .../public-bookings` | 10 / час  | Единственный неаутентифицированный **пишущий** маршрут: каждый запрос     |
|                            |           | забирает реальное окно из календаря мастера                               |

**Кого считаем — не то же, что «откуда пришёл запрос».** Браузеры не обращаются
к API напрямую: они ходят в Next-BFF (`/api/proxy`), который вызывает API
server-to-server. По умолчанию адрес сокета у всех запросов один и тот же, и
лимит «5 гостевых записей в час» означал бы пять на весь продукт, а один шумный
посетитель закрывал бы вход всем. Поэтому `ClientThrottlerGuard` берёт, по
порядку: субъект токена (авторизованный трафик считается по аккаунту — это и
честнее, и осмысленнее адреса, когда мастера сидят за одним NAT); затем
исходный адрес из `X-Forwarded-For`, который BFF передаёт во всех трёх местах,
где обращается к API; затем адрес сокета.

Левое значение `X-Forwarded-For` подставляется клиентом, то есть подделываемо
всем, что может достучаться до API напрямую. В текущей топологии такого пути нет
— BFF единственный вход (см. DEPLOYMENT.md), — и IP используется только для
вызывающих, у которых ещё нет личности. Если API однажды опубликуют напрямую,
этот хоп должен стать подписанным, а не заголовком на честном слове.

Счётчики живут в памяти процесса: при горизонтальном масштабировании лимит
станет «N на инстанс». Перенос на Redis (уже в `REDIS_URL`) идёт вместе с `A-5`.

## 9. Альтернативы и открытые вопросы

1. **REST vs GraphQL:** REST выбран для MVP как более простой в кэшировании (важно для публичных страниц) и предсказуемый в контрактах. GraphQL может быть пересмотрен для Admin/Analytics модуля при росте сложности запросов (Phase 3+) — требует отдельного решения.
2. **OpenAPI-спецификация:** должна поддерживаться в актуальном состоянии параллельно с реализацией (генерация клиентских типов из схемы) — формат/инструмент фиксируется на этапе реализации.
3. **Realtime-обновления** (напр. live-обновление доступности слотов в UI мастера) — кандидат на WebSocket/SSE, вне MVP.
