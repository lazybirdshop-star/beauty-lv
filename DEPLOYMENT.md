# DEPLOYMENT — AMOLIE

Версия 0.1 (черновик для утверждения). Конкретные провайдеры — предложения, требующие подтверждения.

## 0. Фактическое состояние (август 2026)

Ниже описан целевой процесс. Сегодня из него работает:

- **`local`** — полностью: `docker-compose` с Postgres и Redis, миграции Drizzle.
- **CI на GitHub Actions** — четыре шага на каждый PR: `lint`, `typecheck`,
  `test`, `build`. Триггеры — `pull_request` и push в `main`; на рабочих ветках
  CI не запускается, поэтому проверки перед коммитом гоняются локально.
- **Vercel** — деплой фронтенда, статус приходит в commit checks.
- **API на Fly.io** (`amolie-api.fly.dev`, регион `arn` — Стокгольм, рядом с
  базой). Развёрнут с 2026-08-12, машина не засыпает, health-check на `/health`.
- **База — Supabase, регион `eu-north-1` (Стокгольм).** Схема накатана целиком
  (миграции `0000`–`0036`), журнал `drizzle.__drizzle_migrations` заполнен.
  Хранилище изображений — bucket `page-media`: публичное чтение, запись только
  сервисной ролью.

Не поднято: `preview`, `staging`, Sentry.

**Выкатка не автоматическая по обе стороны по-разному, и порядок имеет
значение.** Пуш в `main` выкатывает веб на Vercel сам; API на Fly ждёт ручного
`fly deploy` — сам он после пуша остаётся старым, и `fly secrets set` образ тоже
не меняет. Поэтому: **сначала API, потом пуш веба**. В обратном порядке интерфейс
обещает то, чего сервер ещё не умеет, — и это видно не в логах, а клиенту.

Миграции применяет release-команда (`node dist/database/migrate.js`) в отдельной
машине **до** старта нового кода: упала — выкатка останавливается, прежняя версия
продолжает работать на прежней схеме.

## 0a. Runbook первого запуска

Порядок обязателен: каждый шаг опирается на предыдущий.

**1. API на Fly.io.** `fly.toml` лежит в корне (контекст сборки — корень, образ
собирается по `apps/api/Dockerfile`).

```bash
fly launch --no-deploy --copy-config
fly secrets set \
  DATABASE_URL="<Supabase → Session pooler>" \
  JWT_ACCESS_SECRET="$(openssl rand -base64 32)" \
  JWT_REFRESH_SECRET="$(openssl rand -base64 32)" \
  INTERNAL_PROXY_SECRET="$(openssl rand -base64 36)" \
  SUPABASE_URL="https://<project-ref>.supabase.co" \
  SUPABASE_SERVICE_ROLE_KEY="<Settings → API → service_role>"
fly deploy
curl https://<app>.fly.dev/health   # {"status":"ok","database":"ok",…}
```

`/health` теперь отвечает только после успешного запроса к базе, и `503` от
него означает «машина жива, база недостижима». Проверка стоит в `fly.toml` и
гейтит выкатку: машина с неверным `DATABASE_URL` больше не пройдёт дальше,
притворившись здоровой.

**`INTERNAL_PROXY_SECRET` обязателен в production и обязан совпадать на Fly и
на Vercel.** Это подпись хопа между BFF и API: лимитер считает анонимный
трафик по адресу из `X-Forwarded-For`, а заголовок этот ставит клиент — и API
опубликован в интернет (`[http_service]`), то есть без подписи любой желающий
сбрасывает свой счётчик, меняя строку. При расхождении значений API перестанет
верить адресу от BFF и посчитает всех мастеров одним клиентом; при отсутствии
значения — не поднимется вовсе, и это намеренно.

Порядок при первой установке важен: **сначала переменная на обеих сторонах,
потом выкатка.** Обратный порядок роняет старт API.

Push-уведомления мастеру о новой записи требуют пары VAPID. Она генерируется
**один раз на весь продукт** и ставится отдельным секретом:

```bash
pnpm --filter @amolie/api exec web-push generate-vapid-keys
fly secrets set VAPID_PUBLIC_KEY="<publicKey>" VAPID_PRIVATE_KEY="<privateKey>"
```

Смена пары разом обесценивает все подписки мастеров: устройство подписывается
под конкретный открытый ключ и сообщения, подписанные другим, не принимает.
Без этих секретов API поднимается как обычно, а кабинет честно показывает, что
уведомления недоступны.

Секреты обязаны быть разными и не короче 32 символов — иначе API откажется
стартовать (`env.validation.ts`, и это защита, а не придирка: дефолт лежит в
публичном репозитории). `release_command` применит миграции сам; сейчас они уже
накатаны, поэтому команда отработает вхолостую.

**2. Переменные на Vercel.** `API_URL = https://<app>.fly.dev` для Production.
Без неё фронт стучится в `localhost:3001` — это и есть причина 500 на странице
мастера. Рядом — `INTERNAL_PROXY_SECRET` с тем же значением, что стоит на Fly:
её предъявляют оба места, где BFF ходит в API (`app/api/proxy`, `lib/auth-session.ts`).
Без совпадения лимиты продолжат работать, но посчитают всех мастеров одним
клиентом — то есть первая же нагрузка запрёт всех разом.

**3. Снять защиту доступа.** Settings → Deployment Protection: сейчас включена
Vercel Authentication для всех адресов, кроме собственного домена, и мастера
упрутся в форму входа Vercel.

**4. Production-ветка.** Все деплои сегодня — preview с рабочей ветки, а
production собирается с `main`, где лежит прежний сайт. Пока `main` не обновлён,
по основному адресу открывается старая версия.

**5. Первый администратор.** `pnpm --filter @amolie/api db:seed` с продовым
`DATABASE_URL` — заводит аккаунт админа и печатает пароль один раз. Без него
некому выпустить инвайт-коды мастерам.

**Чего в этом списке нет и почему.** CORS настраивать не нужно: браузер ходит в
API через серверный BFF Next (`/api/proxy`), а серверный запрос не шлёт
`Origin`. Шаблон в `main.ts` понадобится, когда появится домен и поддомены.

## 1. Окружения

| Окружение    | Назначение                                      | Данные                                                                                                                                                                                              |
| ------------ | ----------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `local`      | Разработка на машине разработчика               | Postgres/Redis через `docker-compose.yml` в корне репозитория; если Docker недоступен — нативный Postgres (напр. `brew install postgresql@17`) с теми же credentials, что в `apps/api/.env.example` |
| `preview`    | Автоматическое окружение на каждый Pull Request | Изолированная БД или sandbox-схема, тестовые ключи внешних сервисов                                                                                                                                 |
| `staging`    | Предпродакшн, максимально близкий к production  | Копия структуры production, обезличенные/тестовые данные                                                                                                                                            |
| `production` | Боевое окружение                                | Реальные данные пользователей, регион ЕС                                                                                                                                                            |

Правило: изменения попадают в `production` только через `staging`, никогда напрямую из `local`.

**Сегодня это правило не соблюдается — и это известный долг, а не забытая
строка.** `staging` не поднят (`PF-5`), поэтому выкатка идёт из `local`: локально
прогоняются `lint`, `typecheck`, `test`, `build`, затем `fly deploy` и пуш веба.
Пока продукт носит тестовые данные, цена ошибки — испорченный вечер; с первым
реальным мастером эта строка обязана стать правдой.

## 2. Предлагаемая инфраструктура

Таблица ниже — исходное предложение. Что выбрано на самом деле: **Vercel** (веб),
**Fly.io** (API, регион `arn`), **Supabase** (Postgres `eu-north-1` + Storage,
bucket `page-media`), **Resend** (почта). Redis объявлен в `docker-compose` и в
`REDIS_URL`, но в проде не поднят: очередь (`N-1`) ещё не выбрана. DNS/CDN
отдельным поставщиком не заводились.

| Компонент        | Предложение                                                            | Комментарий                                                        |
| ---------------- | ---------------------------------------------------------------------- | ------------------------------------------------------------------ |
| Frontend hosting | Vercel (или аналог с edge-сетью)                                       | Нативная интеграция с Next.js, автоматические preview-деплои на PR |
| Backend hosting  | Провайдер с ЕС-регионом (напр. Railway/Fly.io/Render)                  | Требование резидентности данных (GDPR)                             |
| База данных      | Управляемый PostgreSQL с ЕС-регионом                                   | Автоматические бэкапы, point-in-time recovery                      |
| Redis            | Управляемый (напр. Upstash), ЕС-регион                                 | Кэш + очередь                                                      |
| Object storage   | S3-совместимое хранилище, ЕС-регион                                    | Фото профилей/услуг                                                |
| DNS/CDN          | Cloudflare или аналог                                                  | DNS, защита от DDoS, edge-кэш статики                              |
| Секреты          | Встроенный секрет-менеджер хостинг-провайдера + `.env` только локально | Секреты никогда не попадают в репозиторий                          |

Финальный выбор провайдеров фиксируется отдельно после сравнения по критериям: соответствие GDPR (регион ЕС), надёжность SLA, стоимость на старте vs. при росте.

## 3. CI/CD Pipeline

Инструмент: GitHub Actions (предложение).

### 3.1. На каждый Pull Request

1. Установка зависимостей (с кэшированием).
2. Линтинг (статический анализ кода).
3. Проверка типов (TypeScript strict).
4. Юнит- и интеграционные тесты.
5. Сборка (build) — проверка, что проект компилируется без ошибок.
6. Деплой в изолированное `preview`-окружение с уникальным URL для ручной проверки.
7. Отчёт о результатах прямо в PR (статус-чеки, обязательные для мержа).

### 3.2. При мерже в основную ветку (staging)

1. Все шаги из 3.1.
2. Применение миграций БД к `staging`.
3. Автоматический деплой backend + frontend в `staging`.
4. (Опционально, по мере готовности) прогон end-to-end тестов на `staging`.

### 3.3. Релиз в production

1. Явное действие (approve/promote) — не полностью автоматический деплой в production на раннем этапе проекта.
2. Применение миграций БД к `production` **перед** выкаткой нового кода, миграции — обратно совместимые (см. [DATABASE.md](DATABASE.md) §6).
3. Поэтапная выкладка (canary/rolling), если поддерживается хостинг-провайдером.
4. Автоматическая проверка health-check после деплоя; при сбое — автоматический откат.

## 4. Ветвление и релизный процесс

- Основная ветка (`main`) всегда деплоится в `staging`.
- Разработка — через короткоживущие feature-ветки и Pull Request (в соответствии с принципом небольших логических изменений из [CLAUDE.md](CLAUDE.md)).
- Промоушен в production — по явному решению, через тег релиза или отдельный production-деплой пайплайна.
- Обязательный код-ревью перед мержем в `main`.

## 5. Переменные окружения и секреты

- Каждое окружение имеет собственный набор переменных (ключи Stripe, SMS/email-провайдера, строка подключения к БД и т.д.).
- Секреты `production` доступны только через секрет-менеджер хостинг-провайдера, не хранятся в файлах репозитория.
- Тестовые/sandbox-ключи внешних сервисов — в `preview`/`staging`, реальные ключи — только в `production`.
- Ротация секретов — процедурно описывается на этапе реализации (владелец процесса — команда/пользователь).

**В `production` API не поднимется без явно заданных значений.** Валидация
окружения (`config/env.validation.ts`) требует `JWT_ACCESS_SECRET` и
`JWT_REFRESH_SECRET` — не короче 32 символов и различные между собой, — а также
`DATABASE_URL` и `REDIS_URL`. Раньше у всех четырёх были рабочие значения по
умолчанию, и это опаснее их отсутствия: секрет подписи, лежащий в этом
репозитории, — не слабый, а публичный (любой подписал бы себе
`role: 'platform_admin'`), а `DATABASE_URL` по умолчанию не падает, а молча
подключается к localhost. Удобный дефолт — именно то, что доезжает до прода
незамеченным, поэтому замечать обязан старт приложения.

`JWT_ACCESS_SECRET` нужен **и веб-приложению**: edge-гейт (`apps/web/src/proxy.ts`,
имя Next 16 для прежнего `middleware.ts`) проверяет подпись токена этим же
секретом. Значения обязаны совпадать, иначе гейт развернёт на `/login` каждого.

## 6. Миграции базы данных

- Применяются как часть pipeline (см. §3), не вручную на боевой БД.
- Каждая миграция проверяется на `staging` перед `production`.
- Ломающие изменения — только в 2 этапа (expand → contract), чтобы избежать простоя при деплое (см. [DATABASE.md](DATABASE.md) §6).

## 7. Мониторинг и алертинг

| Что мониторим                          | Инструмент (предложение)                                                       | Реакция                                                               |
| -------------------------------------- | ------------------------------------------------------------------------------ | --------------------------------------------------------------------- |
| Необработанные ошибки frontend/backend | Sentry                                                                         | Алерт в канал команды при новом типе ошибки/всплеске частоты          |
| Доступность (uptime)                   | Внешний uptime-мониторинг (health-check эндпоинт)                              | Алерт при недоступности > N минут                                     |
| Производительность API                 | APM/трейсинг (встроенный в выбранный backend-хостинг или отдельный инструмент) | Алерт при деградации p95 latency                                      |
| Очередь фоновых задач                  | Метрики очереди (размер, число неудачных задач)                                | Алерт при накоплении failed-джобов (напр. недоставленные напоминания) |
| Биллинг/платежи                        | Вебхуки Stripe + сверка                                                        | Алерт при расхождении статусов платежей                               |

Health-check эндпоинт backend — минимальная проверка доступности БД/Redis, используется хостинг-провайдером и внешним uptime-мониторингом.

## 8. Бэкапы и восстановление (Disaster Recovery)

- Автоматические ежедневные бэкапы БД + point-in-time recovery (глубина — по тарифу управляемой БД, целевой ориентир — не менее 7 дней).
- Регулярная (периодическая) проверка процедуры восстановления из бэкапа на изолированном окружении — не только наличие бэкапа, но и подтверждённая работоспособность восстановления.
- Object storage (фото) — версионирование/резервирование средствами провайдера.
- RPO (допустимая потеря данных) и RTO (время восстановления) — целевые значения фиксируются отдельно при выборе провайдера БД.

## 9. Откат (Rollback)

- Frontend — мгновенный откат на предыдущий deployment (нативная возможность большинства edge-хостингов).
- Backend — откат к предыдущему образу/ревизии при провале health-check после деплоя.
- Миграции БД — откат возможен только для обратимых миграций; необратимые изменения проходят через expand/contract стратегию (см. §6), чтобы откат кода не требовал отката схемы.

## 10. Домены и SSL

- Основной домен `amolie.com` — зарегистрирован 2026-08-08 (+ поддомены при необходимости, напр. для маркетплейс-каталога в будущих фазах).
- TLS-сертификаты — автоматический выпуск/продление через хостинг-провайдера/CDN.
- Принудительный редирект HTTP → HTTPS везде.

## 11. Соответствие требованиям (Compliance)

- Все компоненты, хранящие персональные данные (БД, object storage, логи), — в регионе ЕС.
- Логи не должны содержать чувствительные персональные данные в открытом виде (см. [ARCHITECTURE.md](ARCHITECTURE.md) §16).
- Обработка платежей — через провайдера с сертификацией PCI DSS (Stripe), AMOLIE не хранит данные карт напрямую.

## 12. Открытые вопросы

1. Финальный выбор хостинг-провайдера backend/БД (ЕС-регион) — сравнение вариантов до внедрения.
2. Инструмент APM/трейсинга backend — фиксируется при реализации.
3. Целевые численные значения RPO/RTO — согласуются отдельно, зависят от выбранного провайдера БД.
