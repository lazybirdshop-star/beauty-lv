### Added

- **Финансы у мастера, динамика в админке, группировка навигации (Модуль 5 плана).**
  **Финансы** — новый раздел `/{slug}/dashboard/finance`: выручка, средний чек и доля отмен плитками, столбчатый график выручки по месяцам, разрез по услугам горизонтальными полосами. Backend `GET /organizations/{slug}/finance-summary` агрегирует по снимкам цен в `booking_items` и статусам записей; выручка считается по дате визита (`published_slots.starts_at`), а не по дате создания записи — деньги относятся к моменту, когда услуга оказана. Доля отмен считается от **завершившихся** записей, а не от всех: у ожидающих ещё не было шанса отмениться. **В интерфейсе прямо написано, что это не бухгалтерия** — модуля оплат нет, суммы отражают назначенную стоимость, а не полученные деньги; число, похожее на учёт, но им не являющееся, хуже отсутствия числа.
  **Динамика в админке** — регистрации и записи по неделям за 12 недель, `GET /admin/trends`. **Два отдельных графика, а не один с двумя осями Y:** это разные величины, и общая ось выдумала бы между ними корреляцию (главный анти-паттерн из скилла `dataviz`).
  **Графики** — собственный `BarChart` на вёрстке, без charting-библиотеки: одна серия из десятка значений не требует движка шкал, а любая библиотека либо тянет внешние шрифты, либо конфликтует с токенами. По спецификации скилла: тонкие столбцы со скруглением 4px у вершины, зазор 2px, ненавязчивые оси без линеек, тултип по наведению и с клавиатуры, подпись серии вместо легенды (серия одна), и `sr-only`-таблица с теми же числами — цвет и высота никогда не единственный носитель смысла. Категориальную палитру не валидировал, потому что её нет: везде одна серия акцентным цветом, проверять на цветовую слепоту нечего.
  **Навигация сгруппирована** — у `NavItem` появился `group`, сайдбар рисует подписи секций: у мастера «Работа / Витрина / Бизнес», у админа «Люди / Бизнес / Система». Плоский список из девяти ссылок — то, во что вырождается любая панель; нижняя панель на мобильном группы игнорирует и по-прежнему берёт первые четыре пункта плюс «Ещё». Порядок пунктов мастера изменён так, чтобы в эти четыре попали действительно ежедневные экраны (Главная, Календарь, Записи, Клиенты).
  Проверено вживую: суммы на экране совпадают с API (€105 выручки, €35 средний чек), доля отмен 63% сходится с ручным подсчётом (3 отмены + 2 неявки из 8 завершившихся), обе панели и оба графика рендерятся без ошибок.
- **Календарь: окна стали кликабельными, исправлен перелив времени за плашку.** Цифры времени были выше своей подложки и вылезали за её края — плашка полагалась только на line-height. Плашки перестроены как настоящие кнопки с явной `min-h` и `leading-none`, в обоих видах (неделя и список).
  **Свободное окно** по нажатию открывает шторку с датой и временем — окно можно перенести или удалить. Новый `PATCH /organizations/{slug}/slots/{slotId}`: отклоняет перенос в прошлое (400) и на время, где уже есть окно (409). Ограничение `status = 'available'` стоит **внутри `WHERE`, а не только в предварительной проверке** — между проверкой и обновлением на окно может успеть лечь запись, и молча переехавший визит клиента это ровно тот исход, который здесь обязан быть невозможен.
  **Занятое окно** открывает карточку записи: кто придёт, услуга, стоимость, статус, кнопка звонка, Instagram и заметка. Редактировать оттуда ничего нельзя — чтобы освободить время, мастер должна явно отменить запись в разделе «Записи»; тихий перенос чужого визита хуже лишнего шага.
  Проверено вживую: перенос свободного окна работает, перенос на занятое время — 409, в прошлое — 400, перенос и удаление **занятого** окна — 409 с внятным сообщением.
- **Календарь: недельный вид и публикация окон периодом (TASKS.md B-9).** Публиковать окна по одному — десятки тапов на обычную рабочую неделю, и не было ответа на вопрос «как выглядит моя неделя».
  **Недельный вид** с переключателем «Неделя / Все окна» и навигацией по неделям (стрелки + «Сегодня»): полоса из семи дней с точкой-индикатором (есть свободные / только занятые / пусто), ниже — раскрытые дни с окнами; занятое окно помечено замком и не удаляется, свободное снимается крестиком. **Классическую сетку 7 колонок × часы сознательно не делал:** на 375px ячейка получается около 45px — нечитаемо; мобильный вид должен быть мобильным, а не уменьшенным десктопным.
  **Публикация периодом:** диапазон дат + выбор дней недели (по умолчанию Пн–Пт) + начало/конец дня + шаг 30/60/90/120 мин, с предпросмотром «будет опубликовано N окон» до подтверждения — опубликовать 90 окон по ошибке и снимать их по одному было бы мучительно. Продуктовое ограничение PRD.md §7.4 не нарушено: мастер по-прежнему публикует явные окна, меняется только число тапов на то же действие.
  **Backend** `POST /organizations/{slug}/slots/bulk`: вставка с `onConflictDoNothing` — повторная публикация дня, где часть окон уже есть, это нормальный сценарий, и он не должен падать, а должен дозаполнять пропуски; в ответе честно возвращается, сколько создано и сколько пропущено. Прошедшие времена **отбрасываются, а не отклоняют весь запрос**: диапазон «эта неделя, 10:00–18:00» законно содержит уже прошедшие часы. Дубликаты внутри одного запроса схлопываются до вставки — иначе они конфликтовали бы друг с другом, а не с существующими строками. Размер запроса ограничен 500 окнами.
  Проверено вживую: 12 окон создано, повтор даёт 0 созданных и 12 пропущенных, только прошлое — 400, три одинаковых времени дают одно окно, 501 окно — 400. Расчёт начала недели проверен на воскресенье, понедельник, субботу и переход через год.
- **Главная мастера: ссылка на свою страницу с QR, чеклист первых шагов, история визитов клиента (TASKS.md B-10).**
  **Ссылка и QR.** До этого мастеру негде было взять адрес собственной страницы записи — ядро роста продукта («дай клиенту ссылку») в интерфейсе просто отсутствовало. Теперь на главной есть блок с адресом, копированием в буфер, кнопкой «Открыть» и разворачиваемым QR-кодом. QR рисуется **локально, inline-SVG** (`qrcode.react`), без обращения к внешним генераторам вроде `api.qrserver.com`: ссылка мастера не должна утекать третьей стороне, и внешний сервис в рантайме — лишняя точка отказа. Адрес строится из `window.location.origin`, а не из константы сборки, — чтобы ссылка была рабочей в любом окружении, а не показывала адрес, который не открывается.
  **Чеклист первых шагов.** Новый мастер после регистрации попадал на пустые экраны. Теперь на главной — три шага (добавить услугу → опубликовать окно → получить первую запись), каждый ведёт в нужный раздел. Шаги — реальные предусловия друг друга: без услуг нечего бронировать, без окна — некуда. Блок исчезает сам, когда всё выполнено: постоянный чеклист превратился бы в мебель.
  **История визитов** в карточке клиента: дата, услуга, статус и сумма каждой записи, новые сверху. **Отменённые визиты показываются тоже** — «отменила дважды за месяц» это ровно то, ради чего мастер открывает карточку. Отдельного запроса не понадобилось: записи уже загружены на этом экране, join по телефону тот же, что и у агрегатов.
  Проверено вживую: у опытного мастера чеклист скрыт, у только что зарегистрированного показывает «0 из 3»; ссылка, QR и история отрисовываются.
- **Инвайт-коды и регистрация мастера — продукт наконец может принимать новых пользователей (TASKS.md A-2/A-8/A-12/A-13/O-2/O-7).** До этого таблица `invite_codes` и `GET /admin/invite-codes` существовали, но кодов негде было создать, экрана в админке не было, а эндпоинта регистрации не существовало вовсе — единственный мастер в системе был из сида, и завести второго было нельзя.
  **Общее:** `generateInviteCode()` в `shared-kernel` — формат `XXXX-XXXX` из алфавита без `0/O/1/I/L` (коды диктуют голосом и переписывают от руки), источник случайности — Web Crypto с rejection sampling, а не `Math.random` и не `% max`: остаток от деления смещён к началу 31-буквенного алфавита. Сознательно **Web Crypto, а не `node:crypto`** — пакет импортируется и браузерным бандлом, Node-only импорт затащил бы туда полифил или ошибку сборки. `toOrganizationSlug()` — транслитерация кириллицы и латышских диакритик (NFD + отбрасывание комбинирующих знаков): «Ольга Шмидт» → `olga-shmidt`, «Anna Bērziņa» → `anna-berzina`; имя из одних эмодзи не даёт пустой slug и недоступную страницу.
  **Backend:** `POST /admin/invite-codes` и `PATCH /admin/invite-codes/{id}/revoke` (обе пишут в `audit_log`), `listInviteCodes()` с двумя join'ами на `users` — выдавший и погасивший это разные люди. `POST /auth/register` создаёт пользователя, организацию, членство и гасит код **в одной транзакции**. Код захватывается условным `UPDATE ... WHERE status='active'`, а не проверкой через `SELECT`: два одновременных запроса прошли бы проверку оба (тот же приём, что и захват окна записи). Отзыв возможен только для неиспользованного кода — погашенный уже создал аккаунт. Момент регистрации фиксируется как согласие GDPR (`gdprConsentAt`).
  **Frontend:** новый раздел админки `/admin/invite-codes` — выдача кода с пометкой «для кого» и сроком, копирование в буфер, отзыв с подтверждением, статусы кодов. Страница `/register` из заглушки превращена в рабочую форму: код + имя + email + пароль, после успеха мастер сразу оказывается в своём кабинете. Логика установки httpOnly-cookie вынесена из `login/route.ts` в общий `lib/auth-session.ts` — чтобы флаги cookie не разъехались между двумя копиями.
  **Проверено вживую end-to-end:** выдача кода → регистрация → вход нового мастера → его кабинет и публичная страница отдают 200. Повторное использование кода отклоняется (400), несуществующий код — 400, занятый email — 409, **при неудачной регистрации код остаётся `active`** (не сгорает впустую), коллизия имён даёт `olga-shmidt-2`, повторный отзыв — 404, записи в аудит-логе на месте.
  **Риск, названный явно:** `POST /auth/register` — публичный эндпоинт, создающий аккаунты, а rate limiting (`A-10`) ещё не сделан. В TASKS.md задача помечена как ставшая блокирующей: выпускать регистрацию в открытый интернет без лимитов нельзя.
- **Плитка «Услуг» на главной мастера ведёт в раздел «Цены».** По продуктовому решению плитка выглядит ровно как соседние — без акцентного цвета подписи и без стрелки; о нажимаемости сообщают только press-scale и подсветка фона при наведении. Ссылка появляется **только если мастер не выключила раздел «Цены»** в настройках страницы: иначе клиент попадал бы на страницу, которую она сознательно скрыла (сама страница остаётся доступной по прямой ссылке — флаг управляет навигацией, а не доступом). Проверено вживую в обоих состояниях флага.
- **Карточка услуги на публичной странице: описание и фото примера работы (TASKS.md MD-4/MD-6, доработка).** У `services` появилась колонка `image_url` (миграция `0013`). В форме услуги в кабинете — поле «Фото примера работы» со ссылкой и живым превью: битую или неверную ссылку видно до сохранения. Пустое значение уходит на бэкенд как `null`, а не `''` — иначе валидатор URL отклонял бы очистку поля, а `undefined` означал бы «не менять», и удалить фото было бы нельзя. Проверено вживую: сохранение работает, мусор вместо ссылки отклоняется с 400, `null` очищает фото.
  На публичной странице раздел «Цены» стал интерактивным: строка услуги показывает миниатюру и начало описания, по нажатию открывается шторка с полным описанием, фото примера работы и кнопкой «Выбрать время». Если описания нет — честная строка «Мастер пока не добавила описание», а не пустой блок. Публичный контракт услуги расширен полями `description` и `imageUrl` (раньше отдавались только название, длительность и цена).
  **Ограничение:** это ссылка на изображение, а не загрузка файла — объектного хранилища (R2/S3, ARCHITECTURE.md) в проекте пока нет. Тот же приём уже используется для аватара мастера.
- **Кнопка действия в шторке вынесена из области прокрутки (проп `footer`).** Раньше она была `position: sticky` внутри формы: как только форма становилась выше шторки, кнопка прикреплялась ко дну, а последнее поле (Instagram) проезжало **под ней** — полупрозрачный фон только подчёркивал наложение. Теперь шапка, прокручиваемое тело и футер — три отдельных flex-блока шторки, поэтому кнопка физически не может наехать на контент. Submit работает через `form={formId}` (кнопка живёт вне `<form>`). Сама шторка возвращена к плавающей карточке с отступами от краёв — промежуточный вариант с прижатием к низу экрана отменён как неверно понятая задача. Поле Instagram возвращено в форму как обычное необязательное: сворачивание за ссылку экономило высоту, но стоило лишнего тапа на поле, которое люди заполняют.
- **Выбор услуги в окне записи масштабируется на любой прайс.** Горизонтальная лента карточек заменена на свёрнутый селектор (`ServicePicker`): по умолчанию **одна строка** с выбранной услугой независимо от того, 3 услуги у мастера или 30 — высота шторки перестала зависеть от размера прайса. По тапу раскрывается вертикальный список с ограниченной высотой и собственной прокруткой; при более чем 6 услугах сверху появляется поиск, у пустой выдачи — честное «ничего не найдено» с подсказкой, а не пустой экран. Горизонтальная лента отвергнута сознательно: она прячет большинство вариантов и не даёт понять, что они вообще есть (движок `ui-ux-pro-max`, категории Content/Truncation и Search/Autocomplete). Если услуга всего одна, вместо селектора показывается обычная строка-сводка — контрол, который выглядит нажимаемым, но ничего не делает, был бы обманом. Строки списка — минимум 52px под палец.
- **Время свободных окон набрано тем же шрифтом, что и календарь.** Пилюли со временем были в JetBrains Mono, а числа в календаре — в Onest; рядом это читалось как два разных элемента. Приведено к общему `text-[15px] font-semibold tabular-nums`.
- **Окно записи уплотнено — форма помещается на экран без прокрутки.** Услуги переехали с карточек во всю ширину на горизонтальную ленту компактных карточек: N услуг стоят одну строку высоты вместо N. Дата и время переехали из отдельного блока чипов в описание шапки шторки — место под него уже выделено. Отдельная строка «Итого» убрана, сумма переехала в саму кнопку («Записаться · €35.00»). Необязательное поле Instagram свёрнуто за ссылку «Добавить Instagram» (progressive disclosure) — именно оно раньше вынуждало прокручивать форму ещё до заполнения телефона. Поля, подписи и отступы уменьшены. Итог: типовая форма ≈490px против ≈810px — влезает целиком даже на iPhone SE.
  **Заодно убрано ложное обещание в интерфейсе:** под полем телефона было написано «Для SMS-напоминания за 2 часа до визита», хотя модуль уведомлений (TASKS.md Epic 6) целиком в статусе todo и никакие SMS не отправляются. Строка удалена, а не переписана — телефон и так очевидно нужен для связи.
- **Bottom sheet — плавающая карточка вместо панели во всю ширину, новая анимация.** Шторка отделена от краёв экрана (`inset-x-3`, скруглены все углы), высота ограничена `min(86dvh, 720px)`, тело прокручивается внутри, шапка с заголовком и крестиком закреплена. **Заодно исправлен реальный баг:** раньше шторка росла под контент без ограничения и без внутреннего скролла — длинная форма (например, окно записи после переработки) уезжала за верхний край экрана, и до её начала было не добраться. ### Fixed

- **CI падал на шаге Lint при каждом коммите — как минимум последние 14.** В `turbo.json` задачи `lint` и `typecheck` зависели от `^lint`/`^typecheck`, то есть **не собирали зависимости пакета**. В чистом чекауте (а CI всегда чистый) `packages/shared-kernel/dist` отсутствует, `@beauty-lv/shared-kernel` не резолвится, все его экспорты становятся `any`/error-типами — и типозависимые правила ESLint дают лавину `no-unsafe-assignment`/`no-unsafe-call` в `apps/api`. Локально проблема не воспроизводилась, потому что `dist/` там уже лежал от предыдущих ручных сборок: команда «проходила», хотя проверяла не то же самое, что CI. Обе задачи переведены на `dependsOn: ["^build"]` — как уже было у `build` и `test`. Проверено воспроизведением: с удалённым `dist` и `--force` (в обход кэша turbo) `lint` даёт ровно те же ошибки, что в CI, а после правки весь набор `lint`/`typecheck`/`test`/`build` проходит с нуля.

- **`packages/shared-kernel` не резолвился в рантайме за пределами `apps/web`'s bundler.** Пакет объявлен `"type": "module"` с `main`, указывающим прямо на TS-исходники (`.js`-расширения в импортах — требование `nodenext` для `apps/api`'s typecheck). Next.js транспилирует workspace-пакеты собственным бандлером и не замечал проблемы, но `drizzle-kit push`, `ts-node`-сиды и сам скомпилированный `apps/api` (`node dist/src/main.js`) падали с `ERR_REQUIRE_ESM`/`ERR_MODULE_NOT_FOUND` — пакет физически не запускался вне Next.js. Исправлено по-настоящему: `shared-kernel` получил реальный build-шаг (`tsconfig.build.json`, `pnpm build` → `dist/`), `main`/`types` теперь указывают на `dist/index.js`/`dist/index.d.ts`; `turbo.json`'s `build`/`test` уже зависели от `^build`, так что сборка порядка не потребовала правок пайплайна.
- **Next.js 16: `middleware.ts` → `proxy.ts`.** Framework переименовал конвенцию (`middleware` deprecated, файл и экспортируемая функция теперь `proxy`) — обнаружено по предупреждению живого dev-сервера, переименовано сразу, чтобы не оставлять устаревшую конвенцию в новом коде.
- **Phosphor-иконки в `NavItem` не пересекали границу Server → Client Component.** `admin/layout.tsx` и `[slug]/dashboard/layout.tsx` — Server Components; передача `navItems` (с React-компонентами иконок) как props в клиентский `DashboardShell` падала с `Only plain objects can be passed to Client Components`. Исправлено переносом резолюции `nav-config.ts` внутрь самого `DashboardShell` (уже `'use client'`) — layouts передают только дискриминированный `{ role, slug? }`, ничего не сериализуя через границу.
- **`lib/client-api.ts` тянул `next/headers` в клиентский бандл.** `client-api.ts` импортировал класс `ApiError` из `server-api.ts`, а тот на верхнем уровне импортирует `next/headers` — из-за этого весь файл (а не только используемый класс) попадал в клиентский чанк, и Next падал с "This API is only available in Server Components". Исправлено вынесением `ApiError` в отдельный `lib/api-error.ts` без серверных зависимостей, на который теперь ссылаются оба файла. Та же ошибка повторилась в `features/public-profile`: клиентский `booking-calendar.tsx` импортировал чистую функцию `groupSlotsByDay` из того же файла, где лежали серверные fetch-и — вынесена в отдельный `group-by-day.ts` по тому же принципу.
- **Отменённая запись навсегда блокировала своё окно от повторного бронирования.** `bookings.published_slot_id` был объявлен с плоским `.unique()`, хотя DATABASE.md §3.9 всегда описывал уникальность только среди _активных_ записей — после первой отмены новая запись на то же окно падала с `duplicate key`, несмотря на то, что `published_slots.status` уже честно показывал `available`. Нашлось при живой проверке гостевой записи.
